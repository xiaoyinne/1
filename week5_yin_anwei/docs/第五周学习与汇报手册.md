## 第一章：先用一个现实场景理解整项工作

### 1.1 假设你要安排一辆仓库巡检车

仓库里有一个停车基地S，还有三个需要检查的位置A、B、C。

你给小车的任务是：

```text
从S基地出发
先去A点，车头朝上
再去B点，车头朝左
再去C点，车头朝右
最后回到S基地，车头朝上
```

现实里，A可以代表电表箱前方，B可以代表消防设施前方，C可以代表货架侧面。朝向有用：假如车上装了摄像头，到达设备附近后，摄像头还需要面向设备，才方便检查。

**这是帮助理解的应用场景。本次真正实现的是仿真环境中的到点、转向、连续执行和误差测量，没有实现拍照、识别仪表或判断设备故障。**

### 1.2 小车接到任务后，不会自动知道所有答案

它要解决几个不同的问题。

| 问题 | 本项目由谁解决 | 类比你自己走路 |
| --- | --- | --- |
| 仓库大概长什么样 | 已有地图 | 手里拿着仓库平面图 |
| 我现在在哪里、朝哪边 | AMCL定位 | 看周围环境，确认自己在图上的位置 |
| 到目标应该走哪条路 | NavFn的A*全局规划 | 在图上选一条能走通的路 |
| 现在怎么前进、减速、转弯 | DWB局部控制 | 实际迈步，边走边调整方向 |
| A完成后什么时候去B | Python巡检脚本 | 按任务清单逐项打勾 |
| 到了之后到底停得准不准 | 独立测量程序 | 用尺子、角度尺另外检查 |

这些问题不能只用一个“算法”概括。导航是多个模块配合完成的。

### 1.3 用扫地机器人的例子理解S点

你前面提到扫地机器人从充电位置出发，这个理解很合适。

在任务组织上，可以把S当成“家”：从家出发，完成工作，再回家。

但“回到基地附近”和“把充电触点准确贴合”是不同的技术要求。本次S只是一组仿真目标位姿，没有充电桩模型识别、接触判断和充电对接控制。

因此汇报中可以说“返回基地”，不要直接说“实现了自动回充”。

### 1.4 先记住这段大白话

> 我先给小车一张地图和一个已知的初始位置，再把A、B、C以及返回S的位置和朝向写进任务清单。每去一个点，都由定位模块确认位置、规划模块计算路线、控制模块计算运动速度。脚本等当前任务结束并确认停稳后，再安排下一个点。最后通过Gazebo实际位姿，检查小车是否停在目标附近、车头是否朝向要求的方向。

## 第二章：这周究竟做了什么，有什么用

### 2.1 一句话说明本周工作

**在自己生成的地图对应的仿真场地中，把已有导航系统组织成一项连续巡检任务，并对每一次停车进行独立测量。**

拆开看，有三部分。

1. 每一段导航都使用AMCL定位、NavFn的A*规划和DWB控制。
2. Python程序按S→A→B→C→S的顺序组织任务，并处理失败、超时和停稳条件。
3. 正式运行三轮，记录每段任务状态、实际停车位置和朝向，计算误差。

### 2.2 为什么只有“能去一个点”还不够

假设你每次都在RViz里手动点一个目标。小车能去A，说明一次导航能运行。

如果还要你一直盯着，等它到了A再手动点B、到了B再点C，这项工作仍依赖你持续操作。

现在我们把顺序写进脚本。程序会自己知道下一项是什么，什么时候可以继续，什么时候应该停止。

**价值在于把单次导航变成一个有顺序、有状态判断、有记录的完整任务。**

现实例子：能打开一扇门，与能按照巡楼清单依次检查多扇门，是不同层级的能力。后者需要任务组织。

### 2.3 为什么还要测误差

假设快递软件显示“已送达”，但包裹放在隔壁单元。软件状态完成，并不等于你实际收到了正确位置的包裹。

小车也有类似问题：导航系统按照自己的估计位姿和内部规则返回成功，实际位置仍可能存在偏差。

因此，本周把两个问题分开记录：

- **任务完成了吗？** 看导航Action的最终状态。
- **实际停准了吗？** 看实际位置、朝向和停稳检查。

这让汇报有证据：可以说明哪几段运行成功，也能说明哪一次实际误差超出了标准。

### 2.4 与第四周的区别怎么理解

依据本次任务沿用的材料，第四周已经搭建了地图、仿真场地和导航基础，也已经做过单项导航及停车误差测量。

第五周在这些基础上，重点组织连续巡检：

| 方面 | 本周具体工作 |
| --- | --- |
| 任务数量 | 每轮连续完成四段导航 |
| 任务表示 | 每个目标包含名称、x、y和朝向 |
| 任务顺序 | S出发，依次前往A、B、C，再返回S |
| 执行逻辑 | 等接收确认、等执行结果、检查停稳、决定继续或停止 |
| 到点要求 | A、B、C使用不同固定朝向，返回S保持基地朝向 |
| 数据组织 | 连续任务逐段记录，再按三轮统计每个点的均值、范围和达标次数 |

不要把本周讲成“只换了一个A*算法”。也不要说AMCL、A*、DWB都是自己从头编写的。本次主要调用现有Nav2模块，编写任务组织与测量相关程序。

### 2.5 这项工作的适用范围

它验证的是当前仿真地图、当前参数、已知初值条件下的巡检执行和停车情况。

本次没有完成以下内容：真实机器人部署、未知位置下的全局重定位、自动选择最优巡检顺序、设备检测、自动充电对接、长期可靠性评估。

这些都可以是后续工作，但不能当成本次已完成的成果。

## 第三章：从地图到停车，完整走一遍

### 3.1 先分清三个容易混淆的东西

| 名称 | 含义 | 现实例子 |
| --- | --- | --- |
| Gazebo世界 | 模拟地面、障碍、小车运动和传感器 | 一间可以让车实际运动的“虚拟仓库” |
| 导航地图 | 供定位和规划使用的二维环境表示 | 仓库平面图 |
| RViz | 显示地图、小车、激光、目标和路径 | 查看导航状态的监视屏 |

Gazebo负责模拟“发生了什么”，RViz帮助我们“看见相关数据”。关闭RViz不等于自动停止导航；图形窗口本身也不负责规划路线。

### 3.2 自建地图在这里是什么

本次沿用已有的、由前期点云处理得到的二维地图与对应仿真场地。本周没有在巡检过程中重新建图，也没有把整套FAST-LIO实时里程计接入本次导航运行。

当前导航地图文件包括：

```text
scene_learning/map.yaml
scene_learning/map.pgm
```

`map.pgm`是地图图片。通常浅色表示可通行区域，深色表示障碍；实际占用判定还取决于YAML里的阈值和图像数值。

`map.yaml`是图片的说明书。本次内容的关键部分是：

```yaml
image: map.pgm
resolution: 0.1
origin: [-2.2, -1.8, 0.0]
```

- `resolution: 0.1`：原始地图每个像素边长代表0.1米，即10厘米。
- `origin`：把地图图像放进地图坐标系时使用的原点位姿。
- 单位是米、弧度，不是屏幕像素。

**地图精度与停车误差不是同一个概念。** 地图分辨率是环境表示的粒度；停车误差是实际停车点到目标的距离。原始地图10厘米一格，不表示车只能以10厘米为步长移动，也不保证实际误差一定小于10厘米。

### 3.3 坐标是怎么约定的

在本次PPT的俯视地图显示中：

```text
             +y，90°
                ↑
                |
  180°，-x ←----+----→ +x，0°
                |
                ↓
             -y，-90°
```

这张小图表示地图平面坐标，不表示RViz相机怎样旋转后屏幕永远都一样。

目标位姿写成：

```text
(x, y, yaw)
```

`x、y`表示位置，`yaw`表示车头在平面上的朝向。

例子：同一张课桌前可以站在同一块地砖上，面向黑板，也可以背对黑板。位置相同，朝向不同，因此位姿不同。

### 3.4 本次的目标清单

| 点位 | x / 米 | y / 米 | 目标朝向 | 任务含义 |
| --- | ---: | ---: | ---: | --- |
| S | 0.05 | -0.05 | 90° | 出生基地和最后返回目标 |
| A | 0.05 | 0.65 | 90° | 第一个巡检点 |
| B | 0.85 | 3.25 | 180° | 第二个巡检点 |
| C | -0.80 | -0.10 | 0° | 第三个巡检点 |

出生时已经在S，所以脚本发送的四个目标依次是：

```text
A → B → C → S
```

如果把出生位置一起写进完整路线，就是：

```text
S → A → B → C → S
```

因此是**三个巡检点、一个基地、每轮四次导航任务**。

S→A的请求位置间直线距离是0.70米，它是一段实际任务，不是从A原地开始。路线位置顺序事先指定，程序没有在所有访问顺序中自动寻找最短的一种。

### 3.5 为什么每个点的朝向固定而且不完全相同

不同朝向能验证小车到点后是否能按要求转向，而不只是移动到附近。

三个正式轮次都使用同一组朝向，便于比较重复执行的表现。每轮随机改朝向，会把任务本身也改掉，不利于解释不同轮次的差异。

这里的“固定不同朝向”，可以理解为：A面向一个方向检查，B面向另一个方向检查，C再面向第三个方向检查。

### 3.6 起点已知是什么意思

仿真启动时，把小车出生位置设为S，并给AMCL提供对应的初始位姿。

这相当于告诉人：“你现在大概在这间仓库的这个位置，朝这个方向。”之后他继续依靠观察和运动信息修正认识。

AMCL仍在运行。已知初始位姿是定位的起点，不代表之后的位置永远完全准确。正式程序也给初值设置了协方差，表示初始估计存在分布范围。

这次不是“把机器人放在任意未知位置，让它完全自己找出在哪里”的实验。

### 3.7 一次从S前往A，内部发生什么

```text
1. 程序取出A的目标位姿
2. 向Nav2发送目标
3. AMCL持续提供当前估计位姿
4. 全局规划器利用代价地图计算到目标的路径
5. DWB根据路径、附近障碍和运动约束计算速度
6. Gazebo里的小车按速度运动
7. 新的传感器与里程计信息继续参与定位和控制
8. 导航系统按内部规则结束任务
9. 正式测量程序等待、检查停稳、读取实际位姿
10. 保存状态与误差，符合继续条件后再发送B
```

第3至7步在运行过程中持续配合，不是“定位只做一次，然后只看A*，最后才轮到DWB”。

## 第四章：AMCL、A*、DWB到底各干什么

### 4.1 AMCL：根据观察和运动信息，估计“我在哪里”

AMCL可以先理解成“拿着地图辨认自己位置的模块”。

小车的模拟激光会给出许多方向上的障碍距离。里程计告诉系统小车大概向前移动了多少、转了多少。AMCL结合这些信息与地图，更新小车可能的位置和朝向。

**现实例子：你走进走廊。**

你记得刚才大概向前走了5米，这是类似里程计的信息；你看到左侧门口、右侧墙角与平面图吻合，这是类似环境观测的信息。两种信息结合，比只数自己的步数更可靠。

AMCL使用粒子表示可能的位姿。可以把粒子想成许多张“我可能在这里”的猜测卡片。运动后，这些猜测跟着变化；新的激光与地图匹配后，更符合观测的猜测会获得更高权重。真实算法涉及权重更新和重采样，刚入门时先理解这层含义即可。[AMCL官方参数说明](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/others/configuring_amcl/)

### 4.2 为什么里程计还需要定位修正

如果你闭着眼，只靠自己估计走了几步、每步多长，走得越久，误差通常越容易积累。

小车的轮子也可能存在模拟运动、转弯或估计误差。因此，里程计很适合描述短时间内的相对运动，但需要地图与传感器观测帮助修正全局位置。

不要把“里程计位置”和“地图中的定位位置”当作永远完全相同的数据。

### 4.3 map、odom、base_footprint简单怎么理解

| 名称 | 大白话 |
| --- | --- |
| `map` | 用来描述整个地图环境的坐标参考 |
| `odom` | 以里程计为基础描述连续运动的坐标参考 |
| `base_footprint` | 小车在地面上的参考坐标框架 |
| TF | 告诉程序这些坐标参考之间怎样转换 |

常见关系可以写成：

```text
map → odom → base_footprint
```

想象教学楼有一张统一平面图，每个房间又有自己的测量原点。要把“离房间门口两米”换成“在整栋楼地图上的位置”，就需要知道坐标参考之间的关系。

本次正式程序读取 `map` 到 `base_footprint` 的TF，得到导航系统使用的估计位姿；另从Gazebo读取同一小车参考实体相对世界的实际状态，用于评价。比较的前提是本场地的地图与世界按既有坐标对应关系放置。

### 4.4 A*：决定整段路怎样走

A*是搜索路线的一种方法。本次使用的是Nav2里的NavFn规划器，并设置：

```yaml
use_astar: true
```

它主要回答：从当前估计位置到本次导航目标，可以经过哪些区域？得到的是一条全局路径。

**现实例子：从宿舍到食堂。**

你先看校园图，决定经过哪条路、从哪个门进去。这一层决定路线的大致走向。

路径通常是一系列位置点组成的几何描述，不是一串已经计算好的电机转速。小车能否沿着它实际运动，还需要控制模块。

### 4.5 先用一个教学例子理解A*的评分

下面是理解常见A*思想的抽象例子，不是本次实验测得的代价数值，也不逐行对应NavFn内部实现。

常见写法是：

```text
f(P) = g(P) + h(P)
```

- `P`：正在考虑的候选位置。
- `g(P)`：沿已知候选路线，从搜索起点到P的累计代价。
- `h(P)`：从P到目标剩余代价的启发式估计。
- `f(P)`：用来决定优先探索哪些候选位置的评分。

假设两个候选位置：

| 候选点 | 已走累计代价g | 预计剩余代价h | 评分f |
| --- | ---: | ---: | ---: |
| P | 4 | 6 | 10 |
| Q | 7 | 2 | 9 |

虽然Q的已走代价更大，但预计剩余部分更短，因此A*可能优先扩展Q。评分过程会继续，并不是选中Q后就不再搜索。

启发式是帮助搜索排序的估计，不是提前知道真实未来路线。遇到墙、门、绕路时，剩余直线距离与实际可行路线代价可能不同。

### 4.6 Dijkstra与A*有什么区别

在常见教学模型中：

| 方法 | 排序时主要考虑 |
| --- | --- |
| Dijkstra | 到候选点已经累计的代价 |
| A* | 累计代价，加上剩余代价的启发式估计 |

可以把Dijkstra想成比较均匀地探索，A*则利用目标方向的信息引导搜索。这里说的是搜索思想；具体实现的代价、展开方式和路径提取还要看规划器。

两种方法在同一张地图上，**完全可能给出相同或很相近的最终路线**。区别不一定体现在肉眼看到的小车路线，也可能体现在搜索了多少区域、计算过程和耗时上。本次没有做两种算法在相同条件下的专门性能对照，所以不能宣称“A*一定更快”或“停车更准确都是A*带来的”。

### 4.7 你之前问的“起点到P的路还需要规划吗”

需要。搜索过程必须维护通向候选点的路线代价及关联信息，才能得到完整的路径。

`g(P)`也不是简单地拿尺子量“起点到P的直线长度”。如果中间有墙，它描述的是沿搜索得到的可行候选路线到P的累计代价。

DWB不会接过一个“只知道P在哪里、起点到P怎么走还没管”的半成品任务。它接收的是规划器提供的路径，并结合当前状态进行局部控制。

**结合NavFn源码再补充一句：** 它内部设置搜索端点、传播势场、提取路径的方式，与很多从起点向外画格子的A*教材动画并不完全相同。因此，教材里的g+h适合帮助理解，不要把每个变量都机械套成本项目源码中的同名距离。[NavFn Humble源码](https://api.nav2.org/nav2-humble/html/navfn__planner_8cpp_source.html)

### 4.8 Dijkstra也能在运行中重新规划吗

能。选用哪一种搜索算法，与上层什么时候重新请求规划，是两个层面的问题。

就像手机导航可以定期重新计算路线，内部选用什么路线搜索方法是另一个问题。Nav2可以在任务进行中重新请求全局路径；本次记录里也保存了多次规划结果。

不能把区别讲成“Dijkstra只规划一次，A*会一直规划”。

### 4.9 代价地图是什么

普通地图主要告诉系统哪里可走、哪里是障碍。代价地图还帮助表达“这里虽然未必直接碰撞，但靠近障碍，通行代价较高”。

**现实例子：你推一辆宽小车通过走廊。**

你不会让自己的身体中心刚好不碰墙就满意，还要给车宽和转弯留余量。代价地图会结合机器人尺寸、障碍观测、膨胀等因素，影响路线与控制的选择。

RViz中彩色区域常常是代价地图显示。具体颜色取决于显示配置，不能把某种颜色永远当成一种物理距离。

### 4.10 DWB：决定此刻如何运动

DWB主要回答：“这一小段时间，应该向前多快、向哪边转、转多快？”

它会考虑多组候选速度，预测各组速度对应的短时间轨迹，根据障碍、路径偏离、目标等因素进行评价，选出一组速度指令。执行一小段后，再结合新状态继续计算。

**现实例子：你骑自行车去食堂。**

校园图上已经选好了路线，但遇到转弯时，还要不断调整车把和速度。全局路线与当前动作是配合关系。

本次配置使用 `dwb_core::DWBLocalPlanner`。DWB的轨迹生成和评价器结构，可参考官方说明；本次具体参数以归档中的Humble配置为准。[DWB官方说明](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/controller_plugins/dwb_controller/)

### 4.11 DWB的候选速度举例

下面只是假设，帮助理解，不是实验日志中的实际输出：

```text
方案1：向前0.20米/秒，不转弯
方案2：向前0.15米/秒，向左转0.30弧度/秒
方案3：基本不向前，原地转动
```

如果方案1会靠近障碍，方案2沿路径更合适，方案2就可能得到更好的评分。判断还受运动约束和各评价器参数影响，不是只选“速度最快”的方案。

### 4.12 全局路径、局部预测轨迹、实际轨迹不是一回事

| 名称 | 表示什么 | 本次在哪里出现 |
| --- | --- | --- |
| 全局路径 | 规划器给出的到目标的路线 | `/plan`记录 |
| 局部预测轨迹 | 控制器评估候选速度时预测的短期运动 | DWB内部控制过程 |
| 实际轨迹 | 小车在仿真世界中实际经过的位置 | PPT第6页状态采样图 |

计划路线像你在地图上画的线；实际轨迹像你走完之后留下的脚印。两者可以接近，但不需要逐点完全重合。

### 4.13 “导航闭环”到底闭在哪里

把闭环写成大白话：

```text
观察现在的状态
→ 决定怎么运动
→ 小车发生运动
→ 得到新的观测
→ 再调整后续运动
```

“闭环”的重点是反馈。走一圈回到S，是路线在空间上返回起点；即使只从S走到A，不返回S，导航本身仍然可以是反馈闭环。

### 4.14 当前参数有哪些必须知道，哪些可以暂时不背

| 参数或条件 | 本次设置 | 小白理解 |
| --- | --- | --- |
| 全局规划模式 | NavFn，A*开启 | 使用现成规划器算路线 |
| 局部控制器 | DWB | 根据路径等信息计算当前速度 |
| 内部位置容差 | 0.12米 | 导航内部判定到点使用的位置条件 |
| 内部朝向容差 | 0.10弧度，约5.7° | 导航内部判定到点使用的朝向条件 |
| NavFn搜索容差 | 0.15米 | 附近可用终点搜索的配置 |
| DWB位置容差 | 0.12米 | 目标附近控制使用的位置设置 |
| DWB停止速度参数 | 0.05米/秒 | 控制器使用的停止速度阈值 |
| 外部位置标准 | ≤0.25米 | 实际停车测量的独立要求 |
| 外部朝向标准 | ≤0.25弧度，约14.3° | 实际朝向测量的独立要求 |

0.05米/秒不是本次最高行驶速度。当前配置最高平移速度设置为0.26米/秒。也不要把内部停止速度参数与外部测量的0.01米/秒检查混淆。

刚开始不需要背全部AMCL权重和DWB评价器系数。先掌握每个模块的输入、输出和作用，再逐步理解参数。

## 第五章：巡检程序具体怎样写、怎样执行

### 5.1 先分清“演示程序”和“正式测量程序”

这是本项目特别需要分清的一点。

| 文件 | 具体负责什么 |
| --- | --- |
| `patrol.py` | 定义目标位姿清单；图形演示时顺序发送目标、等待结果、输出耗时 |
| `patrol_measured.py` | 正式单轮测量入口；读取目标清单，调用测量工具逐段执行并保存JSON |
| `measurement_core.py` | 等待系统就绪、发送已知初值、执行导航、采样实际状态、检查停稳和计算误差 |
| `repeat_patrol.py` | 每轮启动新的仿真和导航，执行一轮测量，保存参数快照并清理自己启动的进程 |
| `summarize_patrol.py` | 把多轮原始结果整理成CSV和汇总 |
| `show_patrol_points.py` | 在RViz发布目标标记和目标朝向箭头 |
| `start_week5.sh`、`start_week5.launch.py` | 图形启动入口，加载地图、世界、参数、标记和RViz |
| `nav2_week5_params.yaml` | 保存本组导航参数 |

**PPT里“停稳后记录”的完整流程，对应正式测量程序。普通 `patrol.py` 本身主要等待Action结果，没有独立读取Gazebo实际状态验证停稳，也不负责完整的停车误差统计。**

为什么要分开？平时看演示需要直观方便，正式实验则需要固定条件、完整记录和可核对的数据。用不同入口承担这两种用途，理解起来更清楚。

### 5.2 把目标写成清单

本次 `patrol.py` 中的实际目标定义是：

```python
WAYPOINTS = [
    ("A", 0.05, 0.65, 90.0),
    ("B", 0.85, 3.25, 180.0),
    ("C", -0.80, -0.10, 0.0),
    ("S", 0.05, -0.05, 90.0),
]
```

逐项看第一行：

- `"A"`：方便人辨认的名字。
- `0.05`：目标x坐标，单位米。
- `0.65`：目标y坐标，单位米。
- `90.0`：目标朝向，单位度。

方括号表示一个列表，列表内按顺序保存四个任务。小括号把一个任务的四项信息放在一起。

现实例子：旅游行程单上依次写“博物馆、图书馆、公园、酒店”。列表顺序就是任务顺序。

### 5.3 for循环为什么能自动跑完路线

核心思想是：

```python
for name, x, y, yaw_deg in WAYPOINTS:
    # 用本项的数据完成当前目标
    # 当前项返回后，才处理下一项
    ...
```

第一轮循环取A，第二轮取B，第三轮取C，第四轮取S。

**顺序循环只负责“依次取任务”。让它真的等到当前导航结束，还需要在本次循环里等待接收回复和执行结果。** 如果只连续调用异步发送、完全不等回复，不能仅凭用了for循环就认为任务一定会按预期逐项完成。

### 5.4 发送的目标为什么要包含坐标系

实际代码会设置：

```python
goal.pose.header.frame_id = "map"
goal.pose.pose.position.x = x
goal.pose.pose.position.y = y
```

`frame_id = "map"`是在说：“这些数字要按照地图坐标解释。”

现实例子：你告诉别人“向右两米”，对方需要知道从哪里量、朝哪个方向算右边。只有数字，没有参考坐标，位置描述不完整。

本次所有目标在地图坐标系中给定，不能把屏幕鼠标像素或小车自身坐标直接当成这些地图坐标。

### 5.5 朝向为什么要转换成四元数

清单里用90°、180°，对人容易理解。ROS的目标姿态消息使用四元数保存方向，因此程序要转换。

本次平面运动只需要绕竖直轴的yaw：

```python
yaw_rad = math.radians(yaw_deg)
goal.pose.pose.orientation.z = math.sin(yaw_rad / 2)
goal.pose.pose.orientation.w = math.cos(yaw_rad / 2)
```

此时x、y四元数分量为0。

| 目标朝向 | 弧度 | z、w大致为 |
| --- | --- | --- |
| 0° | 0 | 0，1 |
| 90° | π/2 | 0.7071，0.7071 |
| 180° | π | 1，0 |

四元数的z不是“朝向角本身”。例如90°对应的z约0.7071，不能直接把90填进z字段。

### 5.6 ROS2的节点、话题、服务、Action先怎么分

| 概念 | 大白话 | 本次例子 |
| --- | --- | --- |
| 节点Node | 一个承担某项工作的运行单元 | AMCL节点、巡检客户端节点 |
| 话题Topic | 持续发布或订阅消息的通道 | 激光 `/scan`、规划路径 `/plan` |
| 服务Service | 发出请求，再得到一次回复 | 查询某一时刻Gazebo实体状态 |
| Action | 一项可能持续较久、可提供反馈和请求取消的任务 | `/navigate_to_pose` 导航任务 |

现实例子：温度传感器不断播报温度像话题；问“当前温度是多少”并拿到一次答案像服务；让人搬一批货，期间报告进度，最后给出完成状态，更像Action。

导航通常需要持续一段时间，因此适合使用Action来管理任务。

### 5.7 ActionClient与NavigateToPose分别是什么

实际代码里有：

```python
client = ActionClient(node, NavigateToPose, "/navigate_to_pose")
```

- `ActionClient`：客户端，负责提出任务、接收回复和结果。
- `NavigateToPose`：这个Action使用的消息类型，表示导航到一个目标位姿。
- `/navigate_to_pose`：这项导航能力对应的Action名称。

客户端负责表达“请去这里”。Nav2内部负责组织规划、控制和相关行为，小车的运动不是由Python清单逐条直接设置轮速完成的。

### 5.8 为什么要等两种不同的回复

第一种是**接收确认**：服务端是否接下这项任务。

第二种是**执行结果**：任务最后是成功、取消还是终止失败。

现实例子：你下外卖时，“商家接单”表示接下任务，“订单送达”才表示任务进入最终完成状态。接单时饭还没送到。

因此，程序的逻辑是：

```text
发送目标
→ 等待接收确认
→ 目标被接受后，等待执行结果
→ 再决定是否进入后续处理
```

`goal_handle.accepted`为真，只表示目标被接受，不等于小车到达。

### 5.9 Future与spin是什么

异步调用返回的Future，可以理解成“这件事未来完成后，结果会放进来的对象”。

程序需要持续处理ROS消息，相关回复才能被接收和处理。`spin`、`spin_once`、`spin_until_future_complete`就是相关事件处理方式。

现实例子：你拿到取餐号，需要继续留意叫号。拿到号之后把耳机戴上、完全不接收通知，并不会让后面的通知自动被你处理。

普通演示程序使用 `spin_until_future_complete` 等待；正式测量工具用循环处理消息，同时采集运行状态。

### 5.10 为什么要设置超时

如果通信异常或任务一直没有结束，程序不应该无限等待，也不应该未经确认继续发送后续目标。

本组程序设置了接收确认和导航结果的等待上限。正式测量中，接收回复等待10秒，执行结果等待上限120个墙钟秒。

需要分清：

- 接收回复超时：不能直接断言“服务端肯定没收到”。任务可能已经收到，只是回复没有及时到客户端。
- 结果超时：程序会请求取消当前任务，并处理取消相关回复。
- 退出客户端：不等于已经可靠取消服务端正在执行的任务。

这些处理的作用，是让异常情况有可解释的结束方式。不能把“发出取消请求”直接写成“已经完成取消”。

### 5.11 正式巡检的继续与停止条件

以下伪代码表达流程，不是让你直接替换原程序运行的完整代码：

```python
for target in targets:
    result = 执行导航并等待结果(target)
    stopped, actual_pose = 等待并检查停稳()
    保存状态和测量记录(result, stopped, actual_pose)

    if result == "SUCCEEDED" and stopped:
        continue
    else:
        break
```

这里的继续条件是：**本段Action成功，而且停稳得到确认。**

独立测量发现位置误差超出0.25米，会记录为外部精度未达标，但本次程序不会仅因为这一项误差超出，就自动把Action改成失败或阻止下一项。

所以会出现：本轮四段任务都成功结束，但其中一个点的实际停车精度未达标。这种记录并不矛盾。

### 5.12 本次没有直接使用Nav2的Waypoint Follower

Nav2本身也提供多点任务相关能力。本次采用的是**自定义Python顺序客户端，逐项发送NavigateToPose**。

可以称为“多点巡检脚本”或“顺序目标执行”，但不要把实现说成“调用了Waypoint Follower插件”或“一次调用NavigateThroughPoses走完整条路线”。当前代码不是那样组织的。

## 第六章：停车测量和误差判定怎么做

### 6.1 为什么导航成功后，还要再测一次

导航系统主要依据估计位姿工作。它认为到达，不等于外部实际位置一定符合我们另外规定的标准。

现实例子：你看手机定位，以为自己已经站在商店门口，但实际上还在隔壁店旁边。导航提示结束与实际位置检查是两层信息。

因此，本次用Gazebo提供的实际状态做独立评价。它在仿真场景里充当“外部测量工具”，没有直接作为导航定位结果持续反馈给AMCL。

### 6.2 四种位置数据分别是什么

| 数据 | 从哪里来 | 回答的问题 |
| --- | --- | --- |
| 原始目标位姿 | 目标清单 | 我要求小车最终去哪里、朝哪里 |
| 最后规划终点 | 最后记录的全局路径 | 规划器本次给出的路径到哪里结束 |
| 估计停车位姿 | 地图到小车参考框架的TF | 系统估计自己停在哪里 |
| 实际停车位姿 | Gazebo实际状态服务 | 小车在仿真世界里实际停在哪里 |

当前PPT附录已经把“估计停车位姿”那一列换成了“目标位姿”，便于直接把目标与实际位置对照。原始JSON中仍保留估计值，方便分析问题。

### 6.3 为什么目标与规划终点可能不同

本次NavFn设置了附近终点搜索容差。如果请求目标在当前代价地图条件下不可直接规划，规划器可以尝试附近的可用候选点。

例如第二轮B：

```text
原始目标位置：(0.85, 3.25)
最后规划终点：(0.70, 3.20)
```

最终实际误差仍然与原始B目标比较，不能把目标临时换成更容易接近的规划终点后，再宣称精度达标。

**补充理解：** `tolerance=0.15`是NavFn候选搜索配置。Humble源码按目标附近的x、y范围进行离散候选搜索；它不是“实际停车误差严格不超过半径0.15米”的承诺。不要拿这一个参数当作整套系统的实际误差上限。[NavFn候选搜索源码](https://api.nav2.org/nav2-humble/html/navfn__planner_8cpp_source.html)

### 6.4 为什么要等待至少两个仿真秒

任务刚进入最终状态时，小车可能仍有微小运动或转动，系统中的数据也在继续更新。

本次测量不是看到成功就马上读一个位置，而是给任务结束后的状态留出观察时间。

现实例子：测一个晃动的物体，你会先等它稳定一些，再读尺子。等待有用，但等待本身不保证物体已经不动。

### 6.5 为什么等待之后还要检查速度

因为“已经等了两秒”不能直接推出“现在肯定停稳”。

正式程序要求同时满足：

```text
任务结束后，至少经过2个仿真秒
平移速度 < 0.01米/秒
角速度 < 0.03弧度/秒
```

0.01米/秒相当于1厘米/秒；0.03弧度/秒约为1.72°/秒。

这里说的停稳，是**满足本实验设置的足够小速度阈值**，并不要求浮点速度数据数学上恰好等于0。程序检查的是采样时刻的条件，没有要求连续很长时间都保持低速度，所以不要把它讲成已经做了长时间稳定性验证。

如果等待一段时间后仍未确认停稳，程序停止后续巡检，避免继续假定当前测量有效。

### 6.6 等待两秒会把车刹住吗

不会。等待是测量程序的观察条件，不是刹车指令。

导航控制负责目标附近的运动和任务结束；测量程序负责等待、检查、读取和记录。不能把它解释为“脚本通过sleep两秒主动完成刹车”。

### 6.7 仿真时间与墙钟时间

| 时间 | 含义 | 例子 |
| --- | --- | --- |
| 仿真时间 | 仿真世界里经过的时间 | Gazebo的 `/clock` |
| 墙钟时间 | 电脑现实世界中经过的时间 | 你拿手机秒表计时 |

如果电脑负载较大，现实中过了10秒，仿真里可能只推进了8秒。

本次“任务结束后等两个仿真秒”，按仿真时钟判断；动作耗时和整轮耗时使用单调墙钟计时。当前配置中DWB的 `sim_time=1.7`是短期轨迹预测时域，也不是整个实验时长。

### 6.8 位置误差怎样算

目标位置为 `(x_g, y_g)`，实际停车位置为 `(x_a, y_a)`，计算平面直线距离：

```text
位置误差 = sqrt((x_a - x_g)² + (y_a - y_g)²)
```

现实例子：目标地砖与你实际站立的位置，横向差3厘米，纵向差4厘米，直线距离差就是5厘米，而不是简单相加成7厘米。

这里使用位置差的直线距离，不是沿着小车走过的路线倒着量，也不是Action反馈中的 `distance_remaining`。

### 6.9 朝向误差怎样算

朝向绕一圈会回到同一个方向，因此要取最短角差。

例如本次第三轮B：

```text
目标朝向：180°
实际朝向：约-169.1°
```

`-169.1°`也可以写成`190.9°`，它与180°只差约10.9°，不是349.1°。

程序使用等价于下面的处理：

```python
error = abs(math.atan2(math.sin(actual_yaw - goal_yaw),
                       math.cos(actual_yaw - goal_yaw)))
```

输入和结果先按弧度计算，需要显示时再转成度。

### 6.10 内部到点条件与外部评价条件

这是本次最重要的区别之一。

| 条件 | 使用什么位置 | 本次设置 | 作用 |
| --- | --- | --- | --- |
| 导航内部到点判定 | 系统估计的位姿 | 0.12米、0.10弧度 | 帮助系统决定导航任务是否到达 |
| 外部实际停车评价 | Gazebo实际位姿 | 0.25米、0.25弧度，且停稳 | 独立判断实际误差是否达标 |

内部要求更严格，并不保证外部一定通过，因为估计位姿与实际位姿可能存在偏差，规划终点也可能与原始目标不同。

另外，当前 `SimpleGoalChecker` 使用 `stateful=True`：满足位置条件后会保留这项状态，再检查末端朝向。它不是简单地保证最后采样的x、y、yaw每项都重新同时满足那两个内部数字。该细节在解释个别停车现象时有帮助，不必在普通汇报中展开源码。[Humble到点检查源码](https://api.nav2.org/nav2-humble/html/simple__goal__checker_8cpp_source.html)

### 6.11 怎样判断联合达标

本次外部联合达标要求：

```text
实际位置误差 ≤ 0.25米
且最短朝向误差 ≤ 0.25弧度
且确认停稳
```

注意是“且”，不是“或”。位置合格但朝向不合格，联合仍不合格；朝向合格但位置超出，也一样。

0.25米是25厘米，0.25弧度约14.3°。0.25弧度不是0.25°。

### 6.12 三轮测试怎样控制条件

每一轮都重新启动模拟器和导航，使用相同地图、参数、出生位姿、初始定位信息及目标清单。

但一轮内部的四段任务连续执行，B的起点受前一段A实际停车状态影响，C也受B影响。因此是**三轮完整巡检、共十二次到点测量**，不能说成十二轮各自完全独立的实验。

本次随机种子没有固定，三轮的结果也不能代表所有随机条件和长期运行表现。三轮可以提供重复执行的初步证据，样本量仍有限。

### 7.5 第三轮C点为什么未达标，用数字算一次

```text

Δy = 0.028064 - (-0.100) ≈ 0.128064米
直线距离误差 ≈ 0.260731米，即26.07厘米
```

## 第九章：老师可能问什么，怎样回答

### 9.1 你这周最主要的工作是什么

**回答：** 用Python顺序目标脚本把已有导航组织成S→A→B→C→S的连续任务，给不同目标指定朝向，处理接收、结果、停稳和异常情况，再完成三轮逐点测量与统计。

### 9.2 AMCL、A*、DWB是你自己写的吗

**回答：** 本次调用Nav2已有实现。我的任务工作主要在目标位姿配置、顺序组织、异常处理、实验记录和结果评价，不是从零开发这些基础算法。

### 9.3 为什么有了地图，还需要定位

**回答：** 地图描述环境，但不会自动告诉小车自己在图上的哪里。类似拿着商场平面图，还需要确认自己站在哪个出口。

### 9.4 初始位置是A吗，是任意位置吗

**回答：** 初始位置是固定基地S=(0.05,-0.05)，朝向90°，与A不同。本次每轮出生位姿已知，并给AMCL提供对应初值，不是任意未知起点测试。

### 9.5 三个巡检点为什么会有四次导航

**回答：** A、B、C是三个巡检点，完成后还要返回基地S，所以发送A、B、C、S四个目标。

### 9.6 这是路径最优排序吗

**回答：** 巡检顺序事先指定。A*负责每一段的路径规划，没有在所有A、B、C访问顺序中做自动最优排序。

### 9.7 为什么不同点用不同朝向

**回答：** 位姿包括位置和朝向。不同朝向可以检验目标附近的转向与停车能力，也更接近需要面向设备进行检查的任务形式。三轮使用固定相同朝向，便于重复比较。

### 9.8 是否已经实现自动检查设备

**回答：** 目前实现的是前往检查点、按指定朝向停车和返回基地，没有接入拍照、仪表读数或故障识别模块。

### 9.9 A*与DWB都在“算代价”，是不是重复了

**回答：** 它们考虑的对象不同。A*主要搜索整段全局路径，DWB主要评价当前候选速度对应的短期运动轨迹。好比在地图上选路与骑车时控制车把和速度，两个层面都需要。

### 9.10 A*规划完之后就不再规划了吗

**回答：** 是否重新请求规划由上层导航组织决定，本次运行中有多次规划记录。不能把A*理解成只在开头工作一次，也不能把重新规划当成A*独有能力。

### 9.11 你证明A*比Dijkstra好吗

**回答：** 没有。本次使用A*模式完成任务，没有做两者在相同条件下的专门性能对照。

### 9.12 路线返回S为什么不等于“导航闭环”

**回答：** 返回S描述任务路线。导航闭环描述运动后的观测反馈继续参与定位和控制，即使只从S走到A，也能是闭环导航。

### 9.13 四个目标会同时发送吗

**回答：** 本次逐项发送。等待当前任务的接收确认和最终结果，正式测量确认停稳并记录后，再决定是否发送下一目标。

### 9.14 接收确认超时后怎么办

**回答：** 停止发送后续目标，并保留异常信息。接收回复超时不保证服务端没有接到任务，需要检查当前状态，不能盲目重发。

### 9.15 任务结果超时后怎么办

**回答：** 请求取消当前任务，并处理取消回复及后续状态。不能把“客户端不等了”直接当成“小车任务已经停止”。

### 9.16 导航成功和联合达标为什么不同

**回答：** 导航成功依据系统估计位姿和内部规则；联合达标依据停稳后Gazebo实际位姿的外部检查。本次十二次导航成功，十一回实际位置与朝向同时通过。

### 9.17 参数里是0.12米，为什么评价是0.25米

**回答：** 两个数承担不同作用。0.12米是内部到点判定设置，基于估计位姿；0.25米是独立评价实际停车误差的标准。内部更严格也不能完全消除定位偏差等因素，因此还要测实际误差。

### 9.18 等两秒是不是保证停稳

**回答：** 等待只是一个条件，还需要检查平移和转动速度低于阈值。本次至少等两个仿真秒，检查平移速度小于0.01米/秒、角速度小于0.03弧度/秒后再读数。

### 9.19 为什么不用速度恰好为零作为条件

**回答：** 仿真与浮点数据可能存在微小变化，所以设置足够小的阈值作为本实验的停稳判据。本次不是长时间速度严格为零的验证。

### 9.20 为什么读取Gazebo实际位置，不直接看AMCL

**回答：** AMCL是导航使用的估计。独立评价需要另一份实际状态来核对，避免只用自己的估计证明自己正确。本次Gazebo状态用于评价，没有持续作为定位真值反馈。

### 9.21 第三轮C点未达标，算实验失败吗

**回答：** 导航任务返回成功，但实际位置超出本次精度标准，所以该次联合不达标。记录这个现象是评价工作的一部分；对完整任务执行与精度要求应分别给出结论。

### 9.22 为什么C点平均值合格，却是2/3

**回答：** 均值约0.246米只说明平均水平，第三轮约0.261米仍超过0.25米。逐次判定后再计数，因此是2/3。

### 9.23 第三轮C点偏差到底谁造成的

**回答：** 当前记录能显示估计位置、规划终点与实际停车情况，但还不足以分离所有原因。需要保持其他条件一致，进一步研究定位、目标附近控制和地图场地一致性等因素，不能把原因只归给一个模块。

### 9.24 为什么B有时候规划终点与目标不同

**回答：** NavFn在请求目标不可直接规划时，可以按搜索容差寻找附近可用点。本次仍把实际位置与原始目标比较，目标不会因规划终点变化而重新定义。

### 9.25 为什么180°与-169.1°只差10.9°

**回答：** 角度可以跨越±180°边界。-169.1°等价于190.9°，与180°的最短角差约10.9°。不能直接把两个带符号数相减后取349.1°。

### 9.26 四段耗时相加为什么不等于整轮时间

**回答：** 四段表格统计导航动作阶段，整轮还包括段间准备、停稳等待和状态查询等。本次整轮平均墙钟时间约83.95秒。

### 9.27 你怎么证明每轮用的是同一套配置

**回答：** 正式程序保存了输入文件快照与哈希、运行时关键参数、目标清单和每轮日志。可以从记录核对本组三轮的地图、参数和目标位姿。

### 9.28 这三轮足以说明长期可靠吗

**回答：** 只能说明当前条件下三轮重复运行的初步表现。随机种子没有固定，场地和任务也有限，长期可靠性需要更多轮次和更多条件验证。

**回答：** 本次只返回仿真基地位姿，没有充电桩识别、触点对接和充电状态判断，因此只汇报返回基地。

**图形演示入口与正式误差测量入口有区别。** 图形启动使用原教学世界；正式实验会在世界副本中加入状态测量插件。不要在没有测量服务的图形环境中，直接照搬正式测量客户端并期待得到同样的实际状态数据。

这是预期配置，不是保证每个终端当下都能查询成功。若超时，要先检查节点是否运行、通信域是否相同以及是否加载正确环境。

### 10.8 命令没有输出时，先检查什么

按下面的顺序排查，先查最基础的条件。

1. 当前终端是Ubuntu Bash，还是Windows PowerShell？
2. 当前终端是否执行了 `source /opt/ros/humble/setup.bash`？
3. 当前 `ROS_DOMAIN_ID` 是否与正在运行的导航相同？图形演示为0，本次自动实验为41。
4. 仿真和导航进程是否仍在启动或已退出？
5. `/amcl`、`/planner_server`、`/controller_server` 等是否出现在当前域？
6. 日志是否显示生命周期未激活、缺少初始位姿或TF问题？

`timeout 10s`能限制命令等待时间，但“10秒没回复”本身不能证明节点永久不存在。

必要时可以在当前域检查ROS CLI发现缓存，例如停止CLI守护进程后重新查询。`ros2 daemon stop`主要影响CLI发现服务，不是关闭整个导航系统，不会替你完成小车的任务取消。

### 10.9 停止时怎样操作

在启动相应程序的终端按 `Ctrl+C`。自动正式实验在正常处理结束时会清理自己启动的进程；中途干预后应确认程序状态和清理记录。

关闭RViz图形窗口主要是关闭可视化，不能当作已经取消所有导航任务的证据。也不要在不清楚归属时用一条全局杀进程命令结束所有Gazebo或ROS进程。

### 11.1 容易混淆的概念表

| 容易混淆的说法 | 正确理解 |
| --- | --- |
| 地图上有小车，就不需要定位了 | 地图是环境表示，定位是估计小车在其中的位姿 |
| 有全局路径就能直接控制轮子 | 还需要控制器计算可执行速度 |
| DWB负责A、B、C的访问顺序 | 访问顺序由巡检脚本规定 |

| Dijkstra不能重新规划 | 是否重新请求规划是上层调度问题 |
| 起点到中间候选点的路交给DWB规划 | 全局搜索会维护相关候选路线代价并提取完整路径 |
| Action接受就是已经到达 | 接受与最终结果是两个阶段 |
| SUCCEEDED保证实际位置和朝向都达标 | 本次需要用Gazebo实际状态独立检查 |

| 0.25弧度就是0.25° | 0.25弧度约14.3° |
| 180°与-180°朝向相反 | 两者表示同一个朝向 |

| 返回基地就实现了回充 | 精确对接与充电判断还需单独实现 |

### 11.2 自测题：先遮住答案自己说

**题1：我给B点 `(0.85,3.25,180°)`，这三个数字分别是什么意思？**

答案：地图x=0.85米、y=3.25米，要求最终朝向180°。这是目标位姿，不是实际已经停到的位姿。

**题2：起点是不是A？一轮到底发几个目标？**

答案：起点是S，已经在那里出生。一轮发A、B、C、S四个目标。

**题3：AMCL输出的是什么？**

答案：与定位相关的估计信息，本项目通过TF取得地图中的估计位姿。它不是本次外部评价用的Gazebo实际位姿。

**题4：A*与DWB分别输出什么？**

答案：全局规划器提供路径；DWB根据路径和当前状态等计算运动速度指令。

**题5：为什么还要里程计？**

答案：它提供相对运动信息，帮助连续估计运动；地图与传感器观测再帮助修正全局位姿。

**题6：目标被接受之后，脚本能马上发B吗？**

答案：本次不这样做。要等当前任务最终结果，正式程序再确认停稳、记录，满足继续条件后才发下一项。

**题7：C点实际位置超出，但Action成功且停稳，程序继续吗？**

答案：当前实现会保留外部超出记录，同时按Action成功和停稳条件继续。外部精度与任务状态分开统计。

**题8：计划终点换成附近点后，误差应该相对谁算？**

答案：仍相对原始请求目标算。本次PPT就是这样评价的。

**题9：目标180°，实际-179°，朝向误差是多少？**

答案：约1°，取最短角差。

**题10：三次位置误差0.20、0.24、0.27米，均值低于0.25米，位置达标几次？**

答案：2/3。均值不能替代逐次判定。这组数字是练习题，不是本次某一点的实验记录。

**题11：为什么本次任务12/12成功，而联合达标11/12？**

答案：第三轮C点的位置误差约0.261米，超过0.25米外部标准，但导航任务终态仍为成功，且停稳确认通过。

**题12：本次最核心的两层检查是什么？**

答案：第一层检查任务是否按顺序成功执行；第二层检查实际停车位置和朝向是否符合外部标准。

## 补充答辩：任务结束、精度检查与继续条件

正式测量程序每段结束后，先至少等2个仿真秒并检查速度，再读取实际位姿、计算并保存位置和朝向误差，然后判断是否继续。继续条件是导航Action返回成功且确认停稳，外部误差是否达到0.25米/0.25弧度标准单独统计。第三轮C点虽然位置误差0.261米，但已经导航成功并停稳，因此继续返回S。程序不会根据外部误差自动纠正位姿或重新执行该点，也不会把Gazebo真值直接作为AMCL位置反馈。

如果老师问Dijkstra与A*哪个更好，可以回答：A*把到终点的估计代价用于安排搜索顺序，在估计合适的场景通常能减少搜索量；两种算法都可以输出完整路径，具体路径也可能相同。本次没有只切换算法的同条件对照，不能用两周停车误差证明A*更好。第五周的主要新增工作是连续任务组织、异常处理和逐点测量记录。
