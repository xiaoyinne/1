这周在第四周已经制作好的 Hilti 局部仿真场地中，使用 Gazebo 模拟机器人，使用 AMCL 估计机器人位置，使用 NavFn 的 A* 模式计算路线，再由 DWB 控制机器人运动。随后把手动发送单个目标，逐步改成 Python 脚本自动执行 A→B→A，保存运行日志并录制了带 A、B 标记的演示视频。

## 4. 整套系统怎样配合

```text
已有 Hilti 点云
      ↓ 第四周完成局部投影和场地制作
二维地图 map.yaml / map.pgm      Gazebo 世界 hilti_cells.world
      ↓                               ↓
提供先验环境                    模拟机器人、激光、里程计
      └──────────────┬────────────────┘
                     ↓
                AMCL 估计位姿
                     ↓
巡检脚本给定目标 → Nav2 组织规划和控制
                     ↓
                A* 生成全局路径
                     ↓
                DWB 计算运动速度
                     ↓
                 模拟机器人运动
                     ↓
             激光和里程计随运动更新
                     └──→ 再次用于定位和控制
```

最后一条反馈链就是“闭环”的关键：机器人移动后，系统继续根据新观测调整后面的运动。每一段导航都在闭环运行，巡检脚本则负责在段与段之间安排任务。

Nav2 的行为树会组织规划、跟随和恢复等步骤。因此实际执行中可能重新规划、清理代价地图或出现恢复行为，并不是只算一次路线就一直沿它前进。

## 5. 地图、仿真场地、代价地图分别是什么

### 5.1 二维地图：供定位和导航使用

`map.pgm` 是栅格图片；`map.yaml` 描述图片在哪里、每个像素有多大、地图原点在哪里，以及怎样解释像素值。

本次地图的关键数值：

| 项目 | 数值 | 含义 |
|---|---|---|
| 分辨率 | 0.1 m/格 | 一个像素对应 10 厘米 |
| 尺寸 | 36 列 × 56 行 | 名义覆盖范围为 3.6 m × 5.6 m |
| 原点 | `[-2.2, -1.8, 0.0]` | 栅格地图在地图坐标系中的位置和偏转角 |
| 占据格对应障碍柱 | 393 个 | 沿用第四周生成的场地 |
| 障碍柱高度 | 1.0 m | 仿真几何中的简化障碍高度 |

这些是地图与场地的尺寸，不等于机器人可以通行的有效面积。

### 5.2 Gazebo 世界：让模拟机器人有环境可运动

`hilti_cells.world` 描述 Gazebo 中的障碍、碰撞体、地面和物理环境。机器人传感器会观测这些几何体，机器人也会与碰撞体发生物理交互。

本次场地由二维占据格生成障碍柱，并加入人工平地。它没有恢复原始场景中的全部楼层、台阶、坡度和高度细节。

另外，第四周的白格主要表示选定高度段中点数没有达到占据阈值。**它尚不等于经过真实激光射线验证的安全地面。** 因此当前结论限定在这个简化仿真场地。

### 5.3 代价地图：表达走到某处的代价

RViz 中障碍附近的彩色带来自代价地图显示。障碍周围会设置膨胀区域，使规划和控制倾向于给机器人留出空间。

可把它理解为：墙本身不能穿过，靠墙走也可能需要付出较高代价。这样可以同时考虑障碍和机器人自身尺寸。

全局代价地图服务于较大范围的规划；局部代价地图更关注机器人附近的控制。具体颜色含义取决于 RViz 的配色方案，不能简单认为“所有彩色格子都是实体墙”。

## 6. 定位知识：AMCL、初始位姿和 TF

### 6.1 位姿包含位置和朝向

二维导航中，位姿通常可以写成：

```text
(x, y, yaw)
```

`x、y` 表示位置，单位是米；`yaw` 表示平面内的朝向，单位是弧度。机器人停在同一个位置，朝向不同，后续转弯和行驶过程也会不同。

### 6.2 AMCL 在做什么

AMCL 根据已有地图、激光观测和运动信息，估计机器人在地图中的位置与朝向。它维护多个可能位姿，可以直观理解为一组“我可能在这里”的假设，再用激光与地图的匹配情况更新这些假设。

本次提供了已知初始位置，让估计从一个较小范围开始。它验证的是有初始位姿提示条件下的定位与导航，不能据此宣称完成未知起点全局重定位。

### 6.3 为什么 Gazebo 知道出生点，AMCL 还要初始化

Gazebo 是模拟环境，掌握仿真中的机器人状态。AMCL 则按定位系统的方式工作，要从自己的输入信息估计位姿。两者并不会因为同时启动就自动共享“真实出生位置”。

本次使用的出生初值为：

```text
x = 0.05 m
y = -0.05 m
yaw ≈ π/2，即朝地图 +Y 方向
```

向 `/initialpose` 发布消息，是给定位模块一个初始估计，不会把 Gazebo 中的机器人搬到那里。因此只应在确认小车仍处于对应出生位置时复用这组初值。

### 6.4 协方差表示初值有多不确定

本次初始化消息中，X、Y 方差均为 `0.25 m²`，对应标准差 `0.5 m`；yaw 方差约为 `0.0685 rad²`，对应标准差约 `0.262 rad`。

方差描述不确定程度，不能把 `0.25 m²` 直接读成“初始位置误差只有 0.25 米”。它也和到达目标时的容差是不同的量。

### 6.5 为什么朝向写成四个数

ROS 位姿消息用四元数表示姿态。只考虑平面 yaw 时，可写成：

```text
qx = 0
qy = 0
qz = sin(yaw / 2)
qw = cos(yaw / 2)
```

当 `yaw = π/2` 时，`qz` 和 `qw` 都约等于 `0.7071068`。本周所有巡检目标都使用这个朝向。

### 6.6 TF 是坐标之间的“换算关系”

| 坐标系 | 初步理解 |
|---|---|
| `map` | 整张地图的参考坐标 |
| `odom` | 里程计使用的连续局部参考坐标，会积累漂移 |
| `base_footprint` / `base_link` | 机器人自身的参考坐标 |
| `base_scan` | 本次激光使用的参考坐标 |

常见关系可以概括为 `map → odom → 机器人本体 → 激光`。AMCL 通过定位更新地图与里程计之间的关系；里程计和机器人模型提供其他部分。

当日志提示无法从 `base_link` 变换到 `map` 时，问题可能在坐标链尚未建立。即使地图图片已经显示出来，也不代表定位已经就绪。

RViz 相机还可以旋转。本次视图约旋转了 -90°，所以屏幕上的“上、下、左、右”不能直接当成地图的 +X、+Y。目标坐标始终按 `map` 坐标系解释。

## 7. A* 规划与 DWB 控制怎样分工

### 7.1 A*：找到去目标的路线

A* 用下面的思想组织搜索：

```text
f(n) = g(n) + h(n)
```

`g(n)` 是到当前候选位置已经累计的代价，`h(n)` 是从这里到目标的估计代价。相比只依据已累计代价的 Dijkstra，A* 增加了目标方向的估计来引导搜索。

本次使用 NavFn 插件，在其中设置 `GridBased.use_astar: true`。这是在已有插件中切换算法模式，不是自己实现了 A*。小地图上两种模式的路径可能很相似，因此本周通过读取运行参数确认切换，没有把路径外观当成算法对比实验。[NavFn Humble 官方源码](https://github.com/ros-navigation/navigation2/blob/humble/nav2_navfn_planner/src/navfn_planner.cpp)

### 7.2 DWB：不断决定怎样前进和转弯

有了路线，还需要把路线变成机器人可执行的速度。DWB 会生成若干候选短时运动轨迹，检查轨迹是否合法，并用多个评价项打分，选择运动命令；下一次控制周期再重新计算。

本次配置中包含 `BaseObstacle`、`PathAlign`、`PathDist`、`GoalDist`、`RotateToGoal`、`Oscillation` 等评价项，分别涉及障碍、贴合路径、接近目标、末端朝向和反复运动等因素。相关机制可以在 [DWB Humble 官方源码](https://github.com/ros-navigation/navigation2/blob/humble/nav2_dwb_controller/dwb_core/src/dwb_local_planner.cpp)中查看。

可以这样记：**A* 给出路线；DWB 根据路线和当前状态持续计算速度。**

去程和回程的出发朝向、局部观测、规划路径和控制过程都可能不同，所以即使连接相同两个点，耗时也未必相等。

### 7.3 两类目标容差要分清

| 参数 | 本次值 | 作用 |
|---|---:|---|
| `GridBased.tolerance` | 0.5 m | NavFn 在原目标无法得到有效路径时，允许在附近搜索可达终点 |
| `general_goal_checker.xy_goal_tolerance` | 0.25 m | 到达检查使用的位置距离容差 |
| `general_goal_checker.yaw_goal_tolerance` | 0.25 rad | 到达检查使用的朝向容差，约 14.3° |
| `general_goal_checker.stateful` | `True` | 位置条件满足后记住该结果，随后继续检查朝向 |

这些参数作用在不同环节，不能把两个距离容差直接相加，当作系统保证的最终误差上限。仅凭 `tolerance=0.5`，也不能认定某一次导航实际选用了替代终点。

`stateful=True` 的含义是：位置进入允许范围后，目标检查器可以转入检查朝向的阶段，不再持续重复位置检查。这也是任务成功与最终停车位置需要分别测量的一个原因。[SimpleGoalChecker Humble 官方源码](https://github.com/ros-navigation/navigation2/blob/humble/nav2_controller/plugins/simple_goal_checker.cpp)

## 8. ROS2 知识：节点、话题、参数和 Action

| 概念 | 大白话解释 | 本周例子 |
|---|---|---|
| 节点 Node | 负责一部分工作的程序单元 | AMCL、规划器、巡检客户端 |
| 话题 Topic | 发布和接收消息的通道 | `/initialpose`、`/plan`、`/patrol_waypoints` |
| 参数 Parameter | 节点使用的设置 | `GridBased.use_astar` |
| 服务 Service | 一次请求和对应回复 | 参数查询、生命周期状态查询等 |
| 动作 Action | 持续任务，带接收确认、反馈、结果和取消接口 | `/navigate_to_pose` |

### 8.1 为什么导航使用 Action

“去 B 点”需要持续一段时间，不能只回答“消息发出去了”。程序还需要知道目标是否被接受、执行得怎样、最后是否完成。因此适合使用 Action。

本周代码中有两个关键等待：

```python
send_future = client.send_goal_async(goal)
# 等待这一目标是否被接收。

result_future = goal_handle.get_result_async()
# 等待整个导航任务结束。
```

**目标被接受，意味着可以开始执行；`SUCCEEDED` 才表示任务按系统条件结束。** `spin_until_future_complete` 在等待时处理 ROS 事件，让程序能够收到回复。

### 8.2 通信域与节点发现

本次启动脚本设置了 `ROS_DOMAIN_ID=0`。其他操作终端也需要使用一致的通信域，才能正常发现同一套系统。

本周曾出现 `Node not found` 和 `Unknown topic`，在统一终端环境、刷新节点发现服务后恢复。之后又实际观察到 ROS 后台发现服务异常，排查时使用 `--no-daemon` 绕过它。

应根据检查结果区分：节点没启动、当前终端没发现节点，以及节点存在但请求没有得到回复。它们的处理方法不同。

### 8.3 生命周期 active 表示什么

Nav2 中很多节点有配置、激活等生命周期阶段。`active` 表示节点已进入工作状态；系统仍然需要有效的传感器数据和坐标变换才能完成任务。

## 9. 怎样读懂自己的巡检脚本

主脚本位置：`/home/yaw/nav2_week5/patrol.py`。

### 9.1 路线列表保存“依次去哪里”

```python
WAYPOINTS = [
    ("A", 0.05, 0.65),
    ("B", 0.85, 3.25),
    ("A", 0.05, 0.65),
]
```

一项中依次是名称、X 和 Y。最后再写一次 A，表示回到 A。脚本从机器人当前的位置开始执行，不会在运行前自动重置机器人。

### 9.2 函数负责“一次导航”

`navigate_to_point(node, client, name, x, y)` 完成填写目标、发送请求、等待接收确认、等待结果和判断状态。成功返回 `True`，失败或等待超时返回 `False`。

函数把一段工作整理成可以反复调用的单元，避免为每个点复制整份导航代码。

### 9.3 循环负责“按顺序执行”

```python
for index, (name, x, y) in enumerate(WAYPOINTS, start=1):
    succeeded = navigate_to_point(node, client, name, x, y)
    if not succeeded:
        return
```

这个片段省略了计时和打印，只保留控制顺序。因为函数内部会等待本段结果，所以循环不会一下子把三个目标全部发出去。

本周采用自己写客户端、逐段调用 `NavigateToPose` 的方式，没有调用 Nav2 的 `FollowWaypoints` 接口，也没有加入多点路线排序优化。

### 9.4 超时处理补上了什么

| 环节 | 当前设置 | 超时后的动作 |
|---|---|---|
| 发现导航服务 | 最多 10 秒 | 打印提示并结束 |
| 每次发送目标前 | 处理约 2 秒 ROS 事件 | 给通信发现留出时间 |
| 等待目标接收回复 | 最多 10 秒 | 标记接收状态未知，停止后续巡检点 |
| 等待本段结果 | 最多 120 秒 | 请求取消这段任务 |
| 等待取消回复 | 最多 5 秒 | 打印是否收到取消确认 |

**接收回复超时，只能说明客户端没有按时拿到确认，不能直接判断服务器一定没有接收目标。** 当前脚本不会自动重复发同一点。客户端退出也不等同于服务器目标被取消。

这些处理让等待过程可见、有上限；它们并没有证明底层通信异常已经被彻底消除。取消请求被接受，也需要与机器人最终停止和任务取消完成区分。

### 9.5 计时和日志

计时使用 `time.perf_counter()`，计算“结束读数减去开始读数”。它适合测量经过的实际时间，称为墙钟时间。

当前每段耗时包含发送前约 2 秒的事件处理、通信和等待结果的时间；全程计时在连接服务之后开始。因此它不是单纯的机器人行驶时间，也不是 Gazebo 仿真时间。

`tee` 把终端输出同时显示并写入文件；`2>&1` 把错误输出也合并保存。日志文件名使用上海时区的时间，便于区分多次运行。

### 9.6 为什么标记脚本读取同一个列表

`show_patrol_points.py` 启动时从 `patrol.py` 导入 `WAYPOINTS`，发布 MarkerArray 到 `/patrol_waypoints`。RViz 把这些消息叠加显示成圆点和字母。

这样显示坐标和导航坐标来自同一份定义。标记脚本会去重，所以 A 在路线中出现两次，地图上仍只有一个 A。修改路线后，需要让标记程序重新读取定义。

圆球中心表示目标坐标，字母有少量偏移以免遮挡。绿色 `/plan` 表示当前规划路径，会随重新规划更新；它不是已经走过的完整历史轨迹。

### 10.2 前期手动单点实验的停车测量

下面数据来自前期手动导航后的 Gazebo 终端读数及本次会话记录，**不是最终视频中逐段测出的终点误差**。

| 目标 | 目标坐标 `(x,y)` m | Gazebo 停稳坐标 `(x,y)` m | 位置距离 | 朝向误差 |
|---|---|---|---:|---:|
| A | `(0.05, 0.65)` | `(0.124545, 0.465955)` | 约 0.199 m | 约 19.0° |
| B | `(0.85, 3.25)` | `(0.677882, 3.038810)` | 约 0.272 m | 约 13.7° |

读取命令为：

```bash
timeout 10s gz model -m turtlebot3_waffle -p
```

输出依次为 `x y z roll pitch yaw`，角度单位为弧度。以上距离计算采用当前场景中地图与 Gazebo 世界对应的平面坐标；改换世界原点或地图坐标关系后，需要先进行坐标换算。

位置距离的计算公式：

```text
e = √[(x_actual − x_goal)² + (y_actual − y_goal)²]
```

例如 A 点为：

```text
√[(0.124545 − 0.05)² + (0.465955 − 0.65)²] ≈ 0.19857 m
```

平面朝向误差应取角差绕回 `[-π, π]` 后的绝对值，再按需要换算成度。

### 10.3 为什么返回成功，实际误差仍可能超过容差

有几个环节需要分别检查：

1. Nav2 使用的是估计位姿，Gazebo 读取的是仿真世界中的实际状态，两者可能存在定位偏差。
2. 规划器可能在允许范围内选择附近终点；具体某一轮是否发生，需要记录实际规划路径终点才能确认。
3. 到达检查器启用 `stateful`，先前满足过位置条件后可能继续完成朝向检查。
4. 最后一条导航反馈通常早于停稳采样；其中的 `distance_remaining` 也不应直接当成停稳后到原始目标的直线误差。

因此可以同时记录“Action 成功”和“实际位置距离为 0.272 m”。本周尚未把某一次偏差的原因唯一归因到其中一个环节。

本周的终点位置距离与之前整段轨迹的 ATE 是不同指标。最终带标记视频没有逐段重新测量实际终点误差，也没有进行碰撞接触事件统计。

| 查询不到 AMCL | 当前终端未正确发现节点 | 统一通信域并刷新发现服务 | 先确认环境，再查节点状态 |

| 巡检停在第一段，未打印目标已接受 | 服务端明确记录发送目标接收回复超时 | 结束卡住客户端，添加等待上限与提示，随后重新验证 | 定位卡在哪个等待阶段，不把所有卡住都归为规划失败 |
| B 点附近的小车出画面 | RViz 放大、偏心，边界不足 | 调整中心和缩放，并添加标签 | 演示取景也要覆盖完整任务范围 |

目标回复超时的底层通信原因尚未最终定位。修改后成功跑通了验证和演示，但当前证据不足以声称已证明长期运行稳定。

卡住的那次录屏日志 `demo_20261103_195603.log` 也保留了手动中断后的退出报错，其中包括 `rcl_shutdown already called`。它发生在中断后的资源清理阶段，应与先前已经出现的目标回复超时分开分析；不能把最后打印的异常直接当成最初卡住的原因。

同时，启动日志中曾出现规划失败后清理代价地图、重新规划的记录。因此不能因为最终成功，就概括为“全程没有恢复或重规划”。最终巡检脚本没有自动汇总恢复次数。
