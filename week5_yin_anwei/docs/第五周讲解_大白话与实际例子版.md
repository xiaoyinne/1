# 第五周大白话讲解：我们怎样让小车自己去 B 点，再回到 A 点

> 实验：2026 年 11 月 3 日；讲解整理：2026 年 11 月 4 日。  
> 这份材料先用本周发生的事情讲明白，再介绍对应的专业名字。文中的“值班台、检查点”等是帮助理解的比喻。

## 一、先把这周想成一次“小车跑腿”

假设你管理一栋楼，想让机器人做一次简单巡查：

> 到 A 点确认一下，再去 B 点，最后回到 A 点。

为了方便理解，可以把 A 想成值班台，把 B 想成走廊里的一个检查点。本周实际做的是模拟场地中的到点导航，还没有让小车拍照、读仪表或检查设备。

你只告诉小车“去哪里”，途中怎么绕着障碍走、怎样转弯、什么时候算到达，由导航系统处理。

**这周我们做成的，就是这样一套能自动执行顺序任务的小车导航流程。**

最后一版视频里，终端依次打印：

```text
A 点导航成功
B 点导航成功
A 点导航成功
A → B → A 巡检任务全部返回成功
巡检全程耗时：38.64 秒
```

你可以先记住这句话：

> 我这周让模拟小车在自己已有地图制作的场地里，按照 A→B→A 自动完成了一次路线任务，并保存了日志、录制了视频。

接下来，我们拆开看看：要做到这件事，小车需要解决哪些问题？

## 二、小车要出发，得先回答四个问题

### 1. 楼里哪里有墙、哪里有路？——地图

你去陌生商场，可能先看楼层平面图。机器人也需要一份环境说明。

本周地图不是临时随便画的：之前用 Hilti 数据生成过点云，第四周把其中一小块场景转换成了二维栅格地图和仿真场地，第五周接着使用。

“栅格地图”可以理解成一张铺满小方格的纸，每个格子记录这里是否被占据。

**本周的实际例子：**

```text
地图分辨率：0.1 米/格
```

也就是说，一格代表 10 厘米，连续十格在长度上对应 1 米。地图有 36 列、56 行，对应名义上的 3.6 米×5.6 米区域。里面有障碍，所以并不是这么大一片地方都能让小车通过。

还有一个容易误会的地方：这份地图由点云切片得到，白格主要表示那里没有达到占据判定的点数。要把它用于真实机器人，还需要进一步确认地面和通行情况。本周是在对应的简化仿真场地里验证。

### 2. 我现在站在哪里、朝哪个方向？——定位

有了楼层图，你仍然得找到“您在此处”的那个点。否则看到“去电梯口”，也不知道自己该往哪边走。

机器人解决这个问题的模块，本周叫 **AMCL**。

你可以把它理解为：

> 根据小车看到的墙和障碍，结合刚才移动了多少，猜测自己在地图中的位置，再不断修正这个猜测。

**本周的实际例子：** 刚打开仿真时，Gazebo 中有小车，RViz 中有地图，但地图上没有正常显示小车。日志一直说“请设置初始位置”。

这就像系统已经有一张楼层图，但还没有确定“你在图上的哪里”。我们给 AMCL 一个提示：“刚启动的小车大概在 `(0.05, -0.05)`，朝地图的 +Y 方向。”定位开始工作后，地图中的小车和激光点才显示正常。

这个提示就叫 **初始位姿**。“位”是位置，“姿”是朝向。

注意：给定位提示，不会把仿真中的小车搬到那个位置。小车开走以后，再拿出生点去初始化，就相当于明明已经走到楼另一头，却告诉手机“我还在大门口”，定位会被带偏。

### 3. 从这里到 B，走哪条路？——全局规划

位置确定以后，小车要找一条去 B 的路线。

本周使用的算法叫 **A***，读作“A 星”。

先把名字放一边，可以这样理解：

> 在地图里比较可能的走法，结合已经付出的代价和离目标还可能有多远，决定优先往哪里搜索。

例如有两个候选位置：

| 候选位置 | 已经付出的代价 | 估计到目标还要付出的代价 | 合计 |
|---|---:|---:|---:|
| 甲 | 2 | 1 | 3 |
| 乙 | 1 | 4 | 5 |

这些数只是说明搜索思路。按照这个评分，甲会更值得优先考虑。实际算法还要处理墙、可走格子和地图代价。

这就是常见公式的大白话意思：

```text
总评分 = 已经走过的代价 + 预计剩下的代价
f = g + h
```

第四周的配置用的是 Dijkstra，它主要按已经累计的代价安排搜索。本周按照培养任务启用了 A*。

**本周的实际例子：** 我们查询参数，最初得到：

```text
GridBased.use_astar = False
```

切换后得到：

```text
GridBased.use_astar = True
```

本周是在 NavFn 这个已有规划插件中切换算法模式，没有从零编写 A*。我们确认了模式生效，但没有做“两种算法谁更快、更好”的严格对比实验。

### 4. 路线知道了，每一刻怎么开？——局部控制

导航软件给你画出路线，并不等于你的双脚已经走起来。你还得决定快走、慢走、左转、右转。

机器人这里需要的模块，本周叫 **DWB**。

可以把它想成小车不断问自己：

> 如果我接下来慢慢前进，会到哪里？  
> 如果边走边转弯，会不会离墙太近？  
> 哪一种走法既接近路线，又符合当前运动条件？

DWB 会比较候选的短时运动轨迹，再输出速度命令。过一小会儿，它根据新位置和新观测再算一次。

**本周的实际例子：** 视频里，小车朝 B 移动时，需要沿障碍附近的通道转弯。A* 提供整体路线，DWB 持续决定每一刻的前进和转弯速度。

这样记最方便：

| 模块 | 你可以问它的一句话 |
|---|---|
| 地图 | 这里有什么？ |
| AMCL | 我现在在哪、朝哪里？ |
| A* | 去目标应该走哪条路？ |
| DWB | 我现在应该怎样开？ |

## 三、为什么叫“闭环”？看一次走偏的例子就懂了

假设你蒙着眼睛，按事先背好的指令走：

```text
前进 1 米 → 左转 → 再前进 2 米
```

如果第一步走歪了，后面仍机械地照做，误差就会延续。

正常走路时，你会边看边走：发现靠墙太近，就调整；发现方向偏了，就转回来。

小车的闭环也是这个意思：

```text
看当前情况
    ↓
估计自己在哪里
    ↓
计算路线和运动速度
    ↓
移动一点
    ↓
再看新的情况，再调整
```

**本周的实际例子：** 小车去 B 时并不是“收到指令后一直直着开”。它一边运动，一边更新观测、定位和控制；必要时路线也会重新规划。

另外，“最后回 A 点”和“控制闭环”是两件事：

- A→B→A 描述任务顺序，其中有返回起点的安排。
- 闭环描述运动过程中不断观察、反馈、调整的控制方式。

即使只执行 A→B，这一段导航也可以是闭环的。

## 四、屏幕上的两个大窗口，分别在展示什么

### 1. Gazebo：模拟世界里的小车和障碍

右上角的三维场景是 Gazebo。

可以把它想成一个带物理规则的机器人练习场：里面放了小车、障碍、地面和传感器。小车在这个场地里运动，模拟激光也在这里观测障碍。

本次场地使用障碍柱和人工平地进行简化，没有完整还原真实建筑的楼层、坡度和台阶。

### 2. RViz：把系统里的信息画出来

左边地图窗口是 RViz。

你可以把它想成机器人的工作显示屏：把地图、估计位置、激光、规划路线和标记画出来，方便我们检查。

**本周的实际例子：**

| 画面内容 | 它表示什么 |
|---|---|
| 机器人图标 | 系统在地图坐标中显示的机器人位姿 |
| 红色散点 | 显示的激光观测 |
| 绿色线 | 当前规划路线，会随着重规划更新 |
| 蓝色 A、橙色 B 圆点 | 我们预先设置的目标坐标 |
| 障碍附近的彩色带 | 代价地图中的区域，帮助规划和控制考虑障碍距离 |

其中，绿色线不是已经走过的完整轨迹；A、B 标记也不是本次实际停车位置。

### 3. 为什么墙附近有一圈彩色区域

想象你推一辆小推车穿过走廊。推车有宽度，即使轮子中心没有碰到墙，车身也可能刮墙，所以你通常会留一点距离。

代价地图的障碍膨胀，就帮助系统考虑这种余量。靠近障碍的位置可能有更高代价，规划和控制会据此选择走法。

因此“彩色格子”并不全是实体墙，也不能只看一种颜色就判断那里一定安全可走，要结合地图类型和配置。

### 4. 为什么 B 的坐标较大，却画在屏幕左边

我们使用的 RViz 视图旋转了约 90°。这相当于把一张纸质地图转了个方向。

纸上的坐标没有变，变的是你看它的角度。因此屏幕左边并不一定对应地图的 -X 方向。导航目标始终按照 `map` 坐标系解释。

## 五、你写的 Python 脚本，到底做了什么

先想象：你要给一个跑腿员安排三个任务。你需要先联系上他，再告诉他去哪里，收到完成消息后再交代下一件事。

本周脚本也是这个顺序。

### 1. 先联系上接任务的人

```text
正在等待导航服务……
已连接导航服务
```

这说明程序发现了接收导航任务的服务端。ROS2 里负责发送这种持续任务的客户端，叫 `ActionClient`。

可以把 `Action` 理解成一种带过程和结果的任务：提交任务后，服务器确认是否接收，执行过程中可以提供反馈，最后再告诉你结果，也有取消接口。

### 2. 把路线写成一张任务清单

```python
WAYPOINTS = [
    ("A", 0.05, 0.65),
    ("B", 0.85, 3.25),
    ("A", 0.05, 0.65),
]
```

这一段逐行翻译为：

> 第一件事：去 A，坐标是 `(0.05, 0.65)`。  
> 第二件事：去 B，坐标是 `(0.85, 3.25)`。  
> 第三件事：再去一次 A。

这就是两个不同的点、三次任务。每次运行脚本时，小车都从当前实际位置出发。

### 3. 分清“接了任务”和“完成任务”

```text
目标已接受，正在前往 B 点……
```

就像快递订单已经受理，这时货物还没有送到。

```text
B 点导航成功
```

才相当于收到了完成通知。

所以程序要分别等待这两个回复：

```text
发送目标
  ↓
等接收确认
  ↓
等执行结果
```

代码里的 `send_future` 用于等待接收确认，`result_future` 用于等待导航结果。这里的 `future` 可以理解成“一张等着填结果的回执单”。

### 4. 函数是把“一次导航”整理成一套固定步骤

`navigate_to_point(...)` 负责完成去一个点所需的工作。

类比生活中的“去楼下取快递”：穿鞋、下楼、取件、返回，可以作为一套重复执行的步骤。以后再去取件，不必把每个动作重新解释一遍。

我们的函数同样把“填写目标、发送、等待确认、等待结束、判断成功”放在一起。成功返回 `True`，表示这一段完成；失败或超时返回 `False`。

### 5. 循环负责按清单一项一项做

```python
for index, (name, x, y) in enumerate(WAYPOINTS, start=1):
    succeeded = navigate_to_point(node, client, name, x, y)
    if not succeeded:
        return
```

这段省略了打印和计时，可以这样念：

> 取出下一项任务，执行去这个点的函数。  
> 如果没有成功，整次巡检停止。  
> 如果成功，再取下一项。

函数内部会等结果，所以三个目标不会一下子全部发出去。

### 6. 标记脚本为什么能和巡检脚本配合

`show_patrol_points.py` 读取同一份 `WAYPOINTS`，把坐标画成圆球和文字。

就像你的纸质任务单和墙上的路线图，使用同一份地址。这样不容易出现“标记写在东门，机器人却被要求去西门”的情况。

标记脚本读取路线时，不会自动执行巡检。`patrol.py` 底部的入口判断，让主程序只在直接运行这个文件时启动。

## 六、用本周几个真实问题，理解容易混淆的概念

### 例子 1：为什么在 PowerShell 里执行 printenv 报错

你当时的提示符是：

```text
PS C:\WINDOWS\system32>
```

这是 Windows PowerShell。我们给出的 `printenv` 是 Linux 环境里的命令。进入 WSL Ubuntu 后，提示符变成类似：

```text
yaw@Win202205071328:~$
```

再执行就能读到 ROS 环境信息。

你可以把它理解成：在不同的工作台上，使用各自认识的工具。执行命令前，先看自己现在在哪个终端。

### 例子 2：程序都开着，为什么第二个终端找不到 AMCL

这就像几个人用对讲机，但没有调到同一个频道。

本次启动脚本使用：

```bash
export ROS_DOMAIN_ID=0
```

操作终端也需要使用相同通信域。我们统一了终端环境并刷新发现服务后，第二个终端发现了 `/amcl` 等节点。

后来还实际遇到后台节点发现服务报错。这时使用 `--no-daemon`，可以绕过该后台服务，直接进行发现和查询。

这里要学会区分三种情况：程序没有启动；程序启动了但当前终端没发现；程序已发现但请求没有得到回复。不能看到没输出就一律重启小车。

### 例子 3：地图有了，小车为什么还没出来

假设楼层图挂好了，但你还没有确定“您在此处”的位置，系统就无法把小车放在图上的正确位置。

本周还涉及 **TF**，你可以把它理解成不同参考坐标之间的换算。

例如“距大门 2 米”和“距电梯 2 米”是按不同参照物说的位置。机器人也有地图、里程计、本体和激光自己的参考坐标，需要知道它们怎样对应。

初值到达 AMCL 后，相关地图定位关系建立，导航才能继续工作。重启时曾出现规划器等这项关系、参数查询也没有返回的情况，后来补上初始化并绕过异常的后台发现服务才恢复。

### 例子 4：为什么程序卡在“巡检进度 1/3”

那次程序还没有打印“目标已接受”。检查服务端日志，发现它报告发送目标回复超时。

类比你给跑腿员发消息，系统显示对方在线，但确认回复没有送回来。此时不能仅凭没有回复，就确定对方一定没收到任务。

最初脚本一直等，屏幕没有进一步提示，容易让人误以为小车正在算一条很难的路线。

后来我们改成：

| 等待内容 | 当前处理 |
|---|---|
| 连接导航服务 | 设置 10 秒等待上限 |
| 每次发送前 | 先处理约 2 秒通信事件 |
| 等目标接收回复 | 最多等 10 秒，超时打印提示并停止后续点 |
| 等本段导航结束 | 最多等 120 秒，超时请求取消 |
| 等取消回复 | 最多等 5 秒，并说明是否收到确认 |

这让程序“等什么、等多久、失败后怎样处理”更清楚。后续验证和录制成功，但底层通信异常的具体原因还没有完全定位，不能把“加了等待”说成已经彻底修好了所有通信问题。

### 例子 5：为什么改成 A*，还要保存 YAML

可以把临时改参数理解成“这一次上班口头通知”；保存配置文件则相当于把要求写进正式工作说明。

本周先在运行时启用 A*，再保存到：

```text
/home/yaw/nav2_week5/nav2_week5_params.yaml
```

启动文件里明确指定这份文件。后来重启、完成定位初始化，再查询得到 `True`，才确认新启动流程真的读到了 A* 配置。

## 七、为什么显示“成功”，小车却没有停在圆点正中心

这是这周最值得理解的问题之一。

### 1. “到达”通常允许一定偏差

你让朋友“到门口等我”，通常不要求他的鞋尖压在某一个毫米级坐标上。系统也需要一个明确的到达范围。

本次设置中，目标检查器的位置容差为 0.25 米，朝向容差为 0.25 弧度，后者约等于 14.3°。

朝向也有要求，就像小车到了充电区附近，还要转成规定方向。

### 2. 系统估计的位置，和仿真世界里的位置可能不同

类比手机定位显示你在大门口，但你实际上可能站在旁边几米处。手机根据估计位置判断“已到达”，不代表外部测量一定完全重合。

本周也有两种数据：

- Nav2 使用的估计位置，用于判断和执行导航。
- 从 Gazebo 查询的仿真实际位置，用于检查停在哪里。

### 3. 用 A 点的真实读数算一次

前期一次手动去 A 点后，读到：

```text
目标 A：(0.05, 0.65)
实际停车：(0.124545, 0.465955)
```

两个方向上分别差约 7.45 厘米、18.40 厘米。用勾股定理合成直线距离，约为 **19.9 厘米**。

同样方法，前期去 B 点后的距离约为 **27.2 厘米**。

| 前期手动实验 | 实际位置距离 | 实际朝向偏差 |
|---|---:|---:|
| A 点 | 约 19.9 厘米 | 约 19.0° |
| B 点 | 约 27.2 厘米 | 约 13.7° |

这组数来自前期手动单点测量，最终带标记视频没有逐段重新测量，不能把它们直接当成那段视频的停车误差。

### 4. 还有两个设置会影响怎样理解“成功”

本次目标检查器启用了 `stateful`。可以想成：先打勾“位置进过范围了”，接下来继续检查朝向。在调整朝向时，它不一定反复重新检查位置条件。

规划器还有一个 0.5 米的搜索容差。当原目标无法得到有效路径时，允许在附近搜索可达终点。这和控制器的 0.25 米到达容差作用不同，不能简单相加，也不能只凭这个参数认定某次任务一定换了终点。

实际偏差可能涉及定位、规划终点、到达判定和采样时刻等多个环节。本周还没有把每次偏差唯一定位到其中某个原因。

所以汇报时可以如实说：

> 任务返回成功，同时在前期单点检查中测到了停车偏差。任务能完成与停得多准，需要分别记录。

## 八、38.64 秒究竟表示什么

最终带标记视频对应的实际记录是：

| 段落 | 耗时 | 大白话解释 |
|---|---:|---|
| 当前 A 附近位置 → A | 2.88 秒 | 开始时已经靠近 A，确认任务和调整所需过程较短 |
| A → B | 15.44 秒 | 去程 |
| B → A | 20.32 秒 | 回程 |
| 合计 | **38.64 秒** | 整个脚本的三段任务耗时 |

### 1. 第一段为什么只有两三秒

因为上一轮结束时，小车已经回到 A 附近。你再次运行脚本，它不会自动被搬回出生点，而是从当前的位置开始。

这类似于你本来就在值班台附近，接到“先到值班台”的任务，自然比从大门口走过去快。

而且新版脚本每段发送前包含约 2 秒的通信事件处理，不能把这 2.88 秒全部当作实际行驶时间。

### 2. 回程为什么比去程慢

你从宿舍走到食堂，和从食堂走回宿舍，可能出门朝向不同、绕行不同、途中调整不同，耗时不必完全相等。

小车同样会受出发朝向、定位估计、路线、局部控制、运行负载和通信等待影响。要比较性能，需要控制这些条件，仅凭这一轮不能判断某个算法更好或更差。

### 3. 墙钟时间是什么意思

就是你在现实中拿秒表等了多久。代码通过两次 `time.perf_counter()` 读数相减来计时。

本次时间包含函数内部的通信准备、发送、等待和导航。它与 Gazebo 的仿真时间、机器人真正运动的时间不是同一统计口径。总计时在发现导航服务之后开始。

### 4. 这算不算做了三轮实验

这是一次脚本运行，里面顺序执行了三次任务。它不能写成“三轮独立实验成功率 100%”。

如果要测重复运行稳定性，需要预先固定起点、参数、运行条件和成功标准，再进行多轮记录。本周的主要目标是跑通和演示流程。

## 九、这周到底完成到什么程度

已经有实际代码和视频支持的内容是：

1. 使用已有 Hilti 地图制作的局部场地进行仿真。

你之前算过的 ATE，衡量一段轨迹的误差；这周手动测的终点距离，只检查最后停在哪里。这是两个不同的问题，报告中要使用对应的名字。

## 十二、最后用几个小问题检查自己有没有理解

**问：只有一张地图，小车就能自己走吗？**  
答：还要知道自己在哪里，算路线，再把路线变成运动速度。

**问：A* 直接控制轮子吗？**  
答：A* 负责路线；本周由 DWB 持续计算运动速度，再交给机器人执行。

**问：A→B→A 的“回 A”，就是闭环的意思吗？**  
答：回 A 是任务安排；控制闭环指运动过程中不断观测并调整。它们分别描述不同层面的事情。

**问：收到“目标已接受”，能说小车到达了吗？**  
答：只能说服务器接下了任务，还要等执行结果。

**问：两次运行都成功，是不是说明再也不会卡？**  
答：只能说明这些运行成功。长期稳定性需要有计划的重复验证，本周发生过的通信超时也应保留记录。

**问：图上圆球和小车没有完全重合，是不是一定失败？**  
答：先看任务状态，再测实际误差，还要结合定位、到达条件和规划终点分析。

**问：本周自己做了哪些事情？**  
答：把现有模块连接起来、确认参数生效、写顺序任务脚本、处理等待和超时、记录结果并制作演示。这些是本周系统集成和工具编写的具体工作。
