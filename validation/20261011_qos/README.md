# 2026-10-11：QoS、输入计数与精度对照

目的：解释半速复跑为什么可能只有约 480 个位姿，而不是把“进程正常退出”视为建图成功。测试均为 Hilti exp18 完整单次回放、相同几何/时间/外参配置、相同独立 WSL 工作区。

源 bag：点云 1,094 帧，IMU 43,656 条。测试按顺序执行，没有同时运行多个建图节点。前两组使用同一诊断二进制；随后只增加可选点云可靠性参数和该参数的诊断输出，未改预处理、IMU、滤波或匹配算法。每组的 `source.patch`、二进制 SHA256 和实际 YAML 均可核对。RMW 为本机 `rmw_fastrtps_cpp`；后续可靠组在运行清单中记录了这一项。

## 证据支持什么

1. 原队列组有 614 帧源点云未进入回调。大队列组仍有 486 帧未进入回调，不能用“把队列加大”解释为已经修好。
2. 这些组的接收/同步/跳过/发布计数能对账；记录器行数等于节点发布次数。大量缺失发生在节点回调之前，不是 TUM 导出或轨迹录制阶段少记。
3. 保持大队列、仅改变点云可靠性后，点云与 IMU 都全部进入回调，误差恢复到约 0.2 m。支持在本机、本数据、本回放条件下使用 RELIABLE 的修复方案。
4. 未抓取 RTPS 数据包，也未分别测试大队列中两个深度的影响，不能进一步断言具体是网络分片、DDS 缓冲、某个网卡或 WSL 设置造成的。也不能由一次或少量回放证明所有雷达和机器稳定。

## 尾帧限制：完整接收不等于全部处理

可靠组 A 退出时仍剩 1 帧点云、44 条 IMU。对账为：1,094 收到 = 1,093 同步 + 1 待处理；1,093 同步 = 1 首帧跳过 + 1 初始化空云 + 1 建树 + 1,090 输出。

只读解码原 bag 首尾消息，结果见 [bag_endpoints.json](bag_endpoints.json)，脚本见 [inspect_bag_endpoints.py](inspect_bag_endpoints.py)（运行前 source ROS Humble，文件中的路径对应本次本机数据）。末帧点时间最大值为 1649856337.0184548，最后 IMU 时间为 1649856337.0283704，因此不能把尾帧剩余简单归因于源数据缺少后续 IMU。

源码处理定时器使用 ROS 时钟，bag 结束后 `/clock` 停止；怀疑尾帧与此时定时器不再触发有关，但尚未单独修改验证。因此明确保留约一帧尾部未处理的限制，不称为“所有输入帧全部处理”。这不影响已报告的真值覆盖区间，但不能隐去。
