# 第四周汇报逐页讲解稿

对应文件：[第四周汇报_原理到结果版.pptx](./第四周汇报_原理到结果版.pptx)。共14页，只讲第四周工作。

这份稿子分为“汇报时可以这样说”和“自己要理解的意思”。汇报时讲前者，后者用于准备和回答追问，不需要全部念出来。正常讲解约10～12分钟，可按老师要求压缩。

## 先把整周工作串成一句话

**从已有三维点云中选一小块、选一个高度段，统计出二维障碍格，再用同一份格子生成导航地图和仿真场景，最后让仿真小车在里面定位、规划和运动。**

可以想象在搭一个练车场：点云是场地的测量记录，二维地图是给导航程序看的场地图，Gazebo世界是小车实际练习的虚拟场地。

注意：这个练车场做了人工平地和统一障碍高度的简化，不能等同于原场地的完整复原。

## 第1页：Hilti点云的局部仿真与导航验证

### 汇报时可以这样说

老师好，我这周做的是Hilti点云的局部仿真与导航验证。具体来说，就是把已有点云的一小块区域做成仿真场地，并让小车在里面接收目标、规划路线和运动。

下面我先讲为什么要做这种转换，再讲转换和导航的原理，最后展示实际测试结果和遇到的问题。

### 自己要理解的意思

这周有两件主要工作：**搭建环境**和**验证导航**。既不是重新采集点云，也不是自己从头编写一套导航算法。

**过渡：**“首先，只有点云为什么还不够？”

## 第2页：本周问题——怎样在点云场景里测试导航？

### 汇报时可以这样说

我们手里已有PCD点云，它记录了很多测量点的位置，但这些点还没有直接成为仿真中的地面和碰撞物体。

因此，需要补齐两部分：一部分是给Nav2使用的二维地图，另一部分是给Gazebo使用的地面和障碍。图中展示的就是生成后实际运行过的仿真场景，蓝线是仿真雷达的显示。

本周先完成局部简化环境和单目标导航，为理解整个流程建立基础。

### 自己要理解的意思

点云里“看得到一堵墙”，不代表Gazebo已经知道这堵墙会挡住小车。我们需要生成参与碰撞计算的几何体。

本次采用二维导航方式，所以还需要一份表示障碍位置的二维栅格地图。

### 可能追问

**问：这有什么用？**

答：可以在真实小车运行前，先检查地图转换、软件连接和导航流程能否工作，观察路径和失败情况。但真实部署还需要验证真实地形、传感器、定位误差和安全条件。

**过渡：**“为了生成这两部分，先从点云中选出本次要处理的数据。”

## 第3页：输入处理——先选区域，再选高度段

### 汇报时可以这样说

原始PCD有7042489个点。本次先选取一个3.6米乘5.6米的局部区域，再选取Z在负1.5到负0.8米之间的点。

XY范围决定地图覆盖哪里，Z范围决定哪些高度的点参与后面的投影。这里的负值表示点低于源点云坐标原点，并不表示它在地下。

这个高度段是本次沿用的参考范围，还没有通过地面识别证明它就是最合理的离地障碍范围。

### 自己要理解的意思

选数据相当于做两次筛选：先在大地图里框出一小块，再只保留这一块中某一层高度的点。

本次范围为：

| 方向 | 范围 | 含义 |
| --- | --- | --- |
| X | −2.2到1.4米 | 宽3.6米 |
| Y | −1.8到3.8米 | 长5.6米 |
| Z | −1.5到−0.8米 | 参与投影的参考高度层 |

筛选会减少点数，但**筛选和降采样不同**。本步骤是在输入PCD中选符合条件的点，没有额外进行体素降采样。输入PCD此前是否经过降采样，应以它的生成流程为准。

### 可能追问

**问：高度段是不是根据机器人高度选的？**

答：本次不是严格按机器人高度推导的，而是沿用参考参数。要按实际机器人确定，应先识别地面高度，再结合车身、底盘和传感器等条件判断哪些高度的障碍会影响通行。

**过渡：**“选中的点接下来怎样变成黑白格子？”

## 第4页：投影原理——每个格子统计选中点的数量

### 汇报时可以这样说

投影可以理解成从上往下看，把选中点的XY位置放到二维格子里。本次每格是0.1米乘0.1米，并统计每个格子中有多少点。

例如，一个格子有8个点，达到至少5点的阈值，就标成黑色占据格；另一个格子只有2个点，就输出为白色。

整个区域是36列、56行，共2016格。需要强调，白色只说明这个高度段里的点数不足，不能直接证明那里是安全地面，也可能存在楼梯、缺失或其他没有被这个切片体现的情况。

### 自己要理解的意思

这里不是比较“哪个地方比别处更密”，而是在固定格子大小后，看每格是否达到设定数量。

PPT中的8点和2点是解释规则的例子，不是新增实验测量。

代码里的列号计算为：

```text
col = floor((x - xmin) / resolution)
```

例如，x＝−2.15，地图左边界xmin＝−2.2，两者相差0.05米。每格宽0.1米，所以它落在从左往右第一个格子，即编号0。编号从0开始，不是从1开始。

导出时，本次把不足阈值的格子作为白色自由区域提供给导航使用。**这是简化仿真的建模假设，不是通过真实地面检查得出的结论。**

**过渡：**“因为只统计选定高度中的点，所以换高度会改变输出地图。”

## 第5页：高度段选择——不同切片得到不同障碍轮廓

### 汇报时可以这样说

我比较了两个高度段。负1.5到负0.8米保留43477个点，得到393个占据格；负0.3到0.3米保留576939个点，得到644个占据格。

两组使用相同XY区域、0.1米分辨率和至少5点的规则，只改变高度范围。可以看到，地图上的障碍轮廓明显不同。

本次继续使用第一组作为参考基线。但点更多或者导航更容易成功，都不能单独证明某个高度段更符合真实通行条件。

### 自己要理解的意思

可以把建筑想成多层物体：同一个XY位置，在不同高度可能对应墙、栏杆、桌面或者没有物体。取不同的高度层，从上往下统计出的形状自然不同。

### 可能追问

**问：为什么选第一组？**

答：它来自已有参考场景参数，本周先用它建立可复现的流程，同时保留对比结果。还没有证明它是最优高度段，所以汇报里将它称为参考基线。

**过渡：**“得到占据格之后，同一份数据会用于两个不同文件。”

## 第6页：环境生成——同一份栅格生成地图和世界

### 汇报时可以这样说

同一份占据栅格生成两部分。第一部分是map.pgm和map.yaml，给Nav2读取，告诉导航程序哪些格被标记成障碍。

第二部分是hilti_cells.world，给Gazebo读取，在对应占据格的中心放置柱体。本次每个柱体是0.1米乘0.1米乘1米，底部接触人工平地。

检查确认393个占据格，对应393个碰撞体和393个外观体。这样可以保证导航地图与仿真物体在转换上对应。

### 自己要理解的意思

| 内容 | 通俗含义 |
| --- | --- |
| PGM | 地图的像素图 |
| YAML | 说明图像路径、每像素多少米、地图放在哪里以及颜色读取规则 |
| world | Gazebo的场地文件 |
| visual | 让柱子显示出来的外观 |
| collision | 让小车撞到柱子时会受阻的碰撞几何 |

一个柱子同时有外观和碰撞两种描述，并不是摆了两根柱子。

本次源点云的Z范围与仿真柱体高度是两个不同概念：前者用于选点，后者是我们生成简化障碍时设定的1米高度。没有把源点云的所有真实高度形状原样恢复。

### 可能追问

**问：393个一一对应证明了什么？**

答：证明地图与world的转换一致，包括数量和对应位置。不能据此证明所选高度段正确，也不能证明真实场地中所有白格可通行。

**过渡：**“文件生成后，还需要运行导航程序，才能让车动起来。”

## 第7页：导航原理——小车怎样从当前位置走向目标？

### 汇报时可以这样说

导航过程可以分为定位、规划、控制和反馈。AMCL结合地图和激光估计小车的位置与朝向；全局规划器根据代价地图计算路线；DWB控制器计算当前运动速度；Gazebo接收速度并模拟小车运动。

小车运动后，新的激光和里程计数据继续进入定位与控制过程。ROS2负责这些程序之间的数据通信，RViz用来显示地图、小车和路径，也可以发送目标。

本次使用已有导航模块，没有在仿真中重新运行FAST-LIO建图。

### 自己要理解的意思

用练车来理解各个名字：

| 名字 | 对应角色 |
| --- | --- |
| Gazebo | 虚拟练车场、小车和传感器 |
| Nav2 | 组织“去哪里、走哪条路、怎么开”的导航模块集合 |
| ROS2 | 帮各模块传递数据的通信和运行框架 |
| RViz | 监控与操作面板 |
| AMCL | 根据已有地图和观察估计“我在哪里、朝向哪里” |
| DWB | 结合局部情况和路径计算速度的控制器 |

本次预置NavFn规划器使用Dijkstra模式，不要将其说成“本周实现了A*”。完整巡检任务也没有列为本周成果。

**过渡：**“这些程序的数据来自不同坐标系，还需要让它们对得上。”

## 第8页：坐标与时间——把地图、车和雷达联系起来

### 汇报时可以这样说

雷达可能报告一个障碍在雷达前方1米，但导航还需要知道这个障碍在地图的哪个位置。这就需要把雷达、机体、里程计和地图的坐标关系连接起来。

本次map与odom的关系来自AMCL，odom与机体的关系来自仿真底盘里程计，机体与雷达的安装关系来自机器人模型。TF维护这些关系，使程序能够转换坐标。

机器人在运动，所以关系还与时间有关。相关节点统一使用仿真时间，才能按对应时刻查询变换。

### 自己要理解的意思

下面只是一个不考虑旋转的理解例子：如果雷达在地图坐标中的位置是（2，3），雷达前方1米正好沿地图X正方向，那么这个障碍就在（3，3）。有朝向变化和安装偏移时，计算会更复杂，由坐标变换来处理。

map可以理解成全局地图参照，odom是里程计参照，机体坐标跟着车走，雷达坐标跟着雷达走。

### 可能追问

**问：地图已经显示，为什么机器人还报TF错误？**

答：显示地图只需要读到地图数据。要把机器人或雷达数据显示在map中，还需要完整且时间有效的坐标变换链。

**问：AMCL active是不是说明定位成功？**

答：active表示节点进入活动状态，不保证初始位姿已处理或TF链已经完整，还要继续检查实际数据。

**过渡：**“位置和坐标确定后，还要考虑整辆车能不能从某处通过。”

## 第9页：避障原理——有白格，还要容得下整辆车

### 汇报时可以这样说

导航使用的代价地图在静态地图基础上融合激光障碍，并在障碍附近增加膨胀代价，让规划和控制更倾向于与障碍保持距离。本次膨胀半径是0.55米。

另外，小车不是一个点。本次圆形近似半径是0.22米，参考直径是0.44米。我测量的一处局部窄缝约为0.36米，小于这个参考直径。

所以，即使地图上有连续白格，也需要考虑车身尺寸以及定位、控制余量，不能直接认为车能穿过去。

### 自己要理解的意思

就像人拿着一个宽箱子过门，门里有空隙不代表箱子能通过。对导航而言，路线上的每个位置都要容得下车的占地范围。

膨胀半径0.55米不等于车半径，也不等于距离障碍0.55米内全部禁止通行。具体是否可走还涉及障碍、足迹和代价规则。

### 可能追问

**问：之前不动是不是因为这个窄缝？**

答：目前只能确认这处测线小于参考直径。测线略斜，也没有证明它就是当时失败的必经位置，所以不能把所有失败都归因于它。

**过渡：**“理解这些条件后，下面介绍实际怎样验证。”

## 第10页：验证方法——先检查环境，再发送导航目标

### 汇报时可以这样说

验证分为三个步骤。先检查地图与world对应、激光和时钟有数据，并发布初始位姿，检查定位与TF是否就绪。

然后发送短程、跨区域和绕障目标，也测试静置5分钟后再次发送短程目标。

最后记录Action最终状态、耗时和恢复次数，并结合运动观察和事后位置估计核验。不是只看程序是否启动，或者界面上有没有显示小车。

### 自己要理解的意思

Action可以理解成一个带持续反馈的任务：发送目标后，程序会反馈进度，最后返回成功、失败或取消等状态。

恢复次数表示导航过程中执行恢复行为的计数，**不等于碰撞次数**。单凭这个数字也不能确认每次具体做了什么，需要查看对应日志。

这里的耗时是墙钟耗时，即现实经过的时间。仿真时间可能运行得更快或更慢，因此两者不能混用。

**过渡：**“按照这个方法，记录到了以下结果。”

## 第11页：导航结果——短程与后续绕障均有成功记录

### 汇报时可以这样说

短程目标返回成功，耗时5.83秒，没有恢复；跨区域目标也返回成功，耗时15.85秒，发生1次恢复。

首轮绕障在120秒时限后取消，记录耗时121.95秒，包含取消开销。静置5分钟后的短程任务成功，后续另一次绕障执行也成功，耗时40.89秒，发生3次恢复。

需要说明，后续绕障使用了不同起点，所以这些记录不能作为严格的同条件性能对比。另外，跨区域虽返回成功，事后定位估计仍距请求目标约0.51米，结果还需要结合位置检查。

### 自己要理解的意思

| 测试 | 最终状态 | 恢复次数 | 墙钟耗时 |
| --- | --- | ---: | ---: |
| 短程 | SUCCEEDED | 0 | 5.83秒 |
| 跨区域 | SUCCEEDED | 1 | 15.85秒 |
| 绕障首轮 | 限时后取消 | 14 | 121.95秒 |
| 静置5分钟后短程 | SUCCEEDED | 0 | 4.73秒 |
| 后续绕障执行 | SUCCEEDED | 3 | 40.89秒 |

不要把这五行算成一个“导航成功率”去概括系统性能：它们目的、起点和状态不同，不是统一条件下重复抽样得到的统计实验。

### 可能追问

**问：返回成功，为什么还可能离目标有距离？**

答：成功由系统的任务完成条件和容差判断，不等于实际位置精确重合。规划容差、目标检查容差和定位估计都需要分别核查。这里仅保留Action状态与事后估计距离，不把0.51米直接归因于某个参数。

**过渡：**“下一页展示后续绕障成功那一轮的具体轨迹。”

## 第12页：绕障案例——沿障碍侧面到达目标附近

### 汇报时可以这样说

这轮起点估计约为负0.427、1.370米，请求目标是0.45、负1.45米。蓝线显示小车从障碍另一侧绕行，最后到达目标附近。

Action返回成功，现实耗时40.89秒，过程中有3次恢复。结束后的定位估计距离目标约0.227米。

不过，这条轨迹来自导航反馈中的位置估计，距离也是事后定位估计值，没有独立真值测量，所以不能将它表述为真实物理精度或ATE。

### 自己要理解的意思

看图时可以按“起点、蓝线经过哪里、障碍在哪里、终点和目标星号”的顺序指给老师看，不需要逐个读完坐标。

有3次恢复说明这轮最终完成了任务，但过程还有不顺畅之处，不能说已经实现无恢复的稳定巡检。

**过渡：**“在跑通这些测试的过程中，也遇到了几类实际问题。”

## 第13页：主要问题——显示卡顿、TF异常与初值未生效

### 汇报时可以这样说

第一类是显示和性能问题，包括Gazebo黑屏、RViz操作卡顿。本次通过软件渲染、把RViz帧率降到5 FPS以及减少显示项来处理。

第二类是TF异常和曾经出现的退出挂起，处理时将相关tf2包从0.25.23升级到0.25.24，并保留升级前后的记录。

第三类是AMCL已经active，但初始位姿还没有真正生效，因此重新发布初值，并继续检查TF和节点就绪。处理后完成了本轮导航和等待测试，但还需要更多条件验证稳定性。

### 自己要理解的意思

“界面能打开”“节点active”“初值命令发出”“系统可以导航”是不同层次，不能互相替代。

版本升级后有改善，是本轮观察到的事实；没有完整归因证据时，不应说所有TF错误都由旧版本引起，或者升级以后任何情况都不会再卡。

**过渡：**“最后总结本周已经做到哪里，以及目前结论的范围。”

## 第14页：本周总结——建立局部场景并完成导航验证

### 汇报时可以这样说

本周完成了点云切片和二维栅格转换，生成了对应Gazebo世界并检查一致性，也保留了单目标导航、等待和绕障测试记录。

我的主要理解是：二维地图告诉导航程序哪里被标记为障碍，仿真世界提供碰撞和运动响应，定位、规划与控制模块再让小车在其中执行任务。

目前成果是局部简化仿真环境。人工平地、统一障碍高度和参考Z范围都带有建模假设，白格不能证明真实可通行，仿真成功也不代表已经能直接部署真实小车。以上是本周汇报。

### 自己要理解的意思

本周不是只有“让车动一下”，而是把数据转换、场景构建、软件连接和验证记录连成了完整流程。

但结论应停留在已有证据支持的位置：已经完成所记录的局部仿真测试，尚未验证真实场地通行性和完整巡检。

## 汇报前快速自查

能用自己的话回答下面这些问题，就基本抓住了主线：

1. 为什么PCD之后还要生成地图和world？因为导航需要障碍表示，仿真还需要地面与碰撞几何。
2. 黑格怎么来？选定区域和高度后，在0.1米格子里统计点数，每格至少5点标为占据。
3. 白格代表什么？该切片内点数不足，本次作为仿真自由区域使用，真实可通行性还未证明。
4. 为什么是两个文件支路？地图给Nav2使用，world给Gazebo使用，两者来自同一份栅格。
5. 小车怎么动？定位确定位置，规划选路线，控制算速度，Gazebo执行并持续反馈。
6. TF解决什么？让不同坐标系的数据能按对应时刻联系起来。
7. SUCCEEDED说明什么？该次任务按系统条件完成，不能直接代表精确到达或真实环境安全。

## 没有把握时怎样回答

可以直接说：“这部分本周还没有验证，目前记录支持的是……，要确认还需要……。”例如，高度段是否合理还需识别地面和检查真实通行性，失败原因还需结合当时日志核查。

如果老师问代码分工，可以如实说明：“转换和验证脚本使用了AI辅助，我参与参数操作、场景观察、目标发送和测距，并在梳理每个步骤的作用。”不需要把辅助生成的代码表述为全部独立编写。
